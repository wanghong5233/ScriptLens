## 输出契约

严格 JSON 对象，schema 如下：

```
{{
  "overall_summary": "<= 100 字，本计划要解决什么、预期把哪一维哪个信号补齐>",
  "steps": [
    {{
      "scene_id": "<必须原样来自上面场次清单的 scene_id，不允许编造或拼接>",
      "target_dimensions": ["<维度键，1-3 个，例如 producibility / hook>"],
      "rationale": "<= 130 字：必须点出本场具体哪个角色 / 哪段冲突 / 哪个换景触发了短板。禁止「制作复杂度」「跨集复现」这类无具体指向的模板话术>",
      "expected_changes": "<= 160 字：必须给出可执行的具体改动 — 例如「把第三段陆斯言的台词改为画外音」「合并邢醒到下一场，本场只保留姜栀枝独白」；禁止笼统说「简化」「减少」>"
    }}
  ]
}}
```

## 硬约束

1. **steps 数量 1～{max_steps} 条**，按优先级降序排列；若全剧确无可改场次，
   allow steps = []。
2. **scene_id 必须原样取自场次清单**；不要拼接、不要截断、不要发明。
3. 优先解决最影响投资决策评分的场次（最贴近本次建议 / 诊断信号的几场）。
4. rationale 与 expected_changes 都用中文，**不要复述场次清单原文**，
   提炼后给指令。
5. **主角 / 反派禁止删除**：producibility 类建议**只能**落在配角 / 龙套 /
   无台词工具人 / 换景 / 群戏密度上。如果某场角色全是主角和反派，
   **跳过这场**而不是硬选 — 硬选会被 critic 退回。
6. **rationale 模板话术零容忍**：以下短语在 rationale 中出现一次就算
   step 失败 —
   - 「多个跨集复现角色」「增加了制作复杂度」「降低复杂度」
   - 「一致性负担」「LoRA 复用」「优化人物结构」
   （除非紧跟具体角色名 + 具体场景细节作为证据，否则一律视为模板话术）。
   每条 rationale 至少包含**一个本场具体角色名**或**一句本场具体冲突描述**。
7. 输出必须是合法 JSON 对象，**不要包裹 ```json 代码块，不要附加任何解释文本**。
