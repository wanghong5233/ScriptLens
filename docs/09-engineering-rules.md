# ScriptLens 工程规则沉淀

## 1. 目的

这份文档用于沉淀 ScriptLens 项目中的可复习工程经验。它先作为项目文档存在,不立即写入 `.cursor/rules/`。

原因:

- 当前仍处于立项阶段,规则需要经过实现验证。
- 不把未经验证的想象规则固化为 workspace 约束。
- 先沉淀,后筛选,稳定后再决定哪些进入 Cursor rule。

## 2. 总原则

ScriptLens 的工程目标是高质量交付一个剧本理解 Agent,不是展示复杂架构。

每次实现前先问:

- 这个功能是否直接服务 `docs/source/task.md`?
- 这个功能是否能在 demo 中被评估方看到?
- 这个判断是否能回到原文证据?
- 这个模块是否能被测试或评估?
- 是否存在更简单正确的实现?

## 3. Agent 输出规则

### 3.1 结论必须可验证

任何核心判断都必须带原文依据:

- 是否值得继续看。
- 核心主线。
- 关键人物关系。
- 主要冲突。
- 钩子、反转、爽点。
- 风险和问题。
- 评分理由。

没有依据的内容只能标记为低置信推测,不能作为强结论。

### 3.2 不做普通摘要

禁止把 Agent 输出退化为:

- 一段剧情简介。
- 一份无结构长文。
- 一个聊天机器人回答。
- 一堆泛泛创作建议。

所有输出必须围绕用户决策组织:

- 值不值得继续看。
- 重点看哪里。
- 核心价值是什么。
- 问题和风险在哪里。
- 下一步怎么做。

### 3.3 输出结构稳定

LLM 输出必须经过 schema:

- 后端生成结构化 JSON。
- 前端只消费稳定字段。
- 自由文本只出现在字段值里,不能决定结构。
- schema 变更必须同步 eval 和前端。

### 3.4 评分必须说明依据

禁止只给分数。

每个分数必须包含:

- score。
- level。
- reason。
- evidence_refs。
- improvement。

如果证据不足,分数要降低置信度。

## 4. 证据规则

### 4.1 原文不可丢

任何清洗、分段、摘要都不能丢失原文定位能力。必须保留:

- 原始文本。
- 行号。
- 字符范围。
- segment id。
- evidence ref。

### 4.2 证据粒度优先可读

证据片段不能过长也不能过短:

- 太长:用户无法快速验证。
- 太短:无法支撑结论。

MVP 以段落级证据为底线,后续再做句级证据。

### 4.3 证据和结论要匹配

不能只检索相似片段。证据必须能支持结论。

反例:

- 结论说"人物动机不成立",证据却只是人物出场。
- 结论说"反转强",证据却没有反转信息。
- 结论说"审核风险高",证据没有敏感内容。

## 5. Prompt 规则

### 5.1 Prompt 版本化

所有 prompt 必须独立文件管理:

- `extract_segment_v1`
- `aggregate_report_v1`
- `chat_answer_v1`
- `rewrite_segment_v1`
- `judge_eval_v1`

不要把长 prompt 硬编码在业务函数里。

### 5.2 Prompt 服务 schema

Prompt 的目标是稳定生成 schema,不是写漂亮文章。

每个 prompt 要明确:

- 输入。
- 输出字段。
- 禁止事项。
- 证据要求。
- 失败处理。

### 5.3 不让 prompt 承担工程职责

不要指望 prompt 解决:

- 数据清洗。
- 状态管理。
- 错误处理。
- 重试。
- 证据索引。
- eval。

这些要由代码负责。

## 6. 代码规则

### 6.1 类型优先

所有核心函数签名必须有类型:

- 输入模型。
- 输出模型。
- 错误类型。

Agent 项目最容易失控的地方是"dict 到处传"。核心数据必须用 Pydantic 或等价 schema 收口。

### 6.2 Fail Fast

不能伪造正常结果:

- 解析失败不能返回空报告。
- 抽取失败不能返回空列表冒充成功。
- 证据缺失不能返回强结论。
- LLM 输出不合 schema 不能继续进入前端。

### 6.3 不做 Ghost Layer

禁止只包装一层然后转发:

- 无逻辑的 service。
- 单实现 interface。
- 只代理调用的 manager。
- 没有状态和边界的 agent wrapper。

每个模块必须有真实职责。

### 6.4 配置单一入口

环境变量只在配置模块读取:

- API key。
- model。
- database url。
- upload limit。
- deployment env。

业务代码不散落读环境变量。

## 7. 测试规则

### 7.1 用真实样本

测试 fixture 优先来自真实剧本文本:

- `samples/xiaoqie.txt`。
- 其他短剧/网文/标准剧本片段。

不要手搓过于干净的假样本,否则测不到真实噪声。

### 7.2 测行为不测实现

应该测试:

- 上传文本后能生成报告。
- 报告包含核心字段。
- 结论带证据。
- 追问能返回证据。
- 低分项能触发改写。
- feedback 能影响后续结果。

不应该测试:

- 私有函数调用次数。
- 某个 prompt 的字面内容。
- LLM 内部推理过程。

### 7.3 Eval 是产品能力

评估脚本不是项目附属物,而是加分项和工程护栏。

任何 prompt、schema、模型改动后,都要能跑 eval 看退化。

## 8. 前端规则

### 8.1 前端服务理解效率

前端不是 UI 包装,而是理解工具。

必须优先做好:

- 左原文右分析。
- 证据点击定位。
- 决策卡片。
- 视角切换。
- 分数可解释。
- 改写前后对比。

不要优先做:

- 动画。
- 复杂视觉风格。
- 大量装饰图标。
- 与任务无关的 dashboard。

### 8.2 不把业务逻辑放前端

前端可以做展示和交互状态,不能决定:

- 评分。
- 证据匹配。
- 报告生成。
- 改写策略。
- skill 应用。

这些由后端结构化返回。

## 9. 改写规则

### 9.1 改写必须有目标

不能只说"优化一下"。

改写必须声明:

- 原问题。
- 改写目标。
- 保留约束。
- 改动说明。
- 预期提升。

### 9.2 不自动覆盖原文

改写结果只作为建议展示。

用户未确认前:

- 不替换原文。
- 不修改 evidence。
- 不把改写结果当原文再分析。

### 9.3 改写不做表面润色

改写要围绕:

- 钩子。
- 动机。
- 冲突。
- 节奏。
- 反转。
- 风险降级。

不能只换词、加修辞。

## 10. Skill 规则

### 10.1 Skill 必须可解释

每个 skill 必须说明:

- 解决什么问题。
- 适用什么文本。
- 看哪些维度。
- 输出什么字段。
- 如何影响报告。

### 10.2 Skill 不等于万能记忆

MVP 的 skill 是项目级分析模板,不是跨用户长期记忆系统。

禁止把 skill 做成:

- 黑盒 prompt 拼接。
- 无法关闭的全局规则。
- 用户无法理解的隐式偏好。

### 10.3 反馈必须可追踪

用户反馈影响结果时,要能看到:

- 哪条反馈。
- 影响了哪个结论。
- 是否生成 skill。
- 是否应用到下一次分析。

## 11. 部署规则

### 11.1 Key 不进仓库

API key 只走环境变量和 `.env.example`。

禁止:

- 硬编码 key。
- 在日志打印 key。
- 在前端暴露 key。

### 11.2 Demo 优先稳定

线上 demo 必须优先保证:

- 示例剧本能跑。
- 错误可见。
- API 超时有提示。
- 冷启动可接受。

不要在 D9-D10 引入新架构。

## 12. 文档规则

文档要回答评估方关心的问题:

- 你如何理解这个问题。
- 为什么不是摘要问题。
- 核心用户需求是什么。
- 输出结构为什么这样设计。
- Agent 在什么情况下有效。
- Agent 在什么情况下失效。
- 做了哪些取舍。

文档不写:

- 无关项目背景。
- 空泛愿景。
- 没有实现路径的复杂概念。

## 13. 可以进入 `.cursor/rules` 的候选规则

实现验证后,可以考虑抽取以下规则:

- 任何核心分析结论必须带 evidence refs。
- 所有 LLM 输出必须经过 schema 校验。
- 评分必须包含 reason 和 evidence。
- 改写必须声明目标和保留约束。
- Agent 功能必须能映射到用户决策问题。
- prompt、schema、eval 必须同步版本化。

这些规则现在先保留在本文档中,等 build 阶段验证后再固化。
