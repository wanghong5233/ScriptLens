# 情节标签设计决策

更新时间：2026-05-25

本文档定义剧本解析（ScriptLens）侧情节标签的对象边界、字段集、抽取流程、与视频素材标签体系的对接关系。事实源仅有两份：

1. `docs/素材标签体系.md`（2026-05-22 版，标签体系唯一事实源）
2. `ScriptLens/eval/爆款短剧剧本（完整本）/《云总你的小心肝重生了》1-100.docx`（剧本结构实证样本，100 集 210 场）

其他历史 1on1 笔记、任务边界 V1、过往 demo 实现（包括 ScriptLens 当前的「看点 / highlights」逻辑）均不作为事实源；新方案视为完全重写。

## 1. 剧本结构实证

样本：100 集 210 场，自动统计如下。

| 指标 | 数值 |
| --- | --- |
| 总集数 | 100 |
| 总场数 | 210 |
| 每集场数（min / median / max） | 0 / 2 / 5 |
| 每场行数（min / median / max） | 1 / 15 / 75 |
| △ 动作描述总数 | 1316 |
| OS / VO 内心独白总数 | 226 |
| 对白行数 | 1981 |

场的结构边界完全机械可切：每场以 `\d+-\d+ <地点> <日/夜> <内/外>` 开头，后跟 `人物：...`，再交替 `△ 动作描述` / `角色名：台词` / `角色名OS：` / `角色名vo：`。闪回明确包在 `【闪回开始】` / `【闪回结束】` 之间（实例：81-2）。

## 2. 「场」与「情节」不是同一对象

「场（scene）」是剧本写作的**结构单元**：同一时空、同一人物组合下的连续戏，按 `X-Y 地点 时段 内/外` 显式标号。  
「情节单元（plot unit / beat）」是叙事的**戏剧动作单元**：一次目标/状态的推进或转折。

两者多对多：

- 一场可包含 1~7 个情节单元。短过渡场只有 1 个，长高潮场可达 5~7 个。
  - 实例：场 1-1（38 行）= 4 个情节单元（求救 → 拒绝 → 自轻献身 → 交易达成）
  - 实例：场 40-2（6 行）= 1 个情节单元（下单跟踪）
- 一条情节弧可跨多场。
  - 实例：「工地死人案」= 78-x → 79-x → 80-1 → 81-1 → 81-2 闪回 → 82-1，共 6 场。

## 3. 标签的载体是情节单元，不是场

视频素材投流的最小内容单元 ≈ 30~60s ≈ 一个戏剧动作单元（参见 `素材标签体系.md` §6 `duration_bin`）。  
如果标签只打到场级，长场内并存的「打脸 + 反转 + 情感选择」会被压成一组复合标签，与视频素材侧按 beat 切分的标签层 join 会失真。

因此 ScriptLens 的标签载体定义为：

```text
script
└── episode（集，结构单元）
    └── scene（场，结构单元，正则切分）
        └── plot_unit（情节单元，语义切分）  ← 标签打在这一层
            ├── line_range: [start_line, end_line]
            ├── summary: 一句话描述
            └── plot_tags: 10 维 enum（6 原始 + 4 派生）
```

场仍然作为外层结构容器（提供时空、人物组合上下文），但**所有 plot 标签字段挂在 plot_unit 上**。

## 4. ScriptLens 在标签体系里的产出边界

`素材标签体系.md` 共 5 大类标签，剧本是纯文本，能稳定产出的只有 plot 这一类。

| 类别 | ScriptLens 是否产出 | 原因 |
| --- | --- | --- |
| 剧级标签 `drama_tags` | 否 | 文档明确「来自榜单和剧数据源中的已有标签」，是开放离散集（重生、战神、先婚后爱…），不该由剧本文本反推。剧 ID 携带的现有 `drama_tags` 直接透传。 |
| 画面标签 `visual_tags` | 否 | 色温、光线、镜头、调色等需视频帧。 |
| ASR 台词标签 `asr_tags` | 否 | 面向成片台词节奏 / CTA / 旁白结构，与剧本台词文本不同对象。剧本台词不应混用此维度。 |
| 情节原始 6 维 `plot_*` | 是 | 文档语义全部针对叙事文本：plot_hook / conflict_type / story_stage / relationship_arc / payoff_type / emotional_driver。 |
| 情节业务 4 维 `business_*` | 是（由 6 维派生） | 文档明确「业务粗粒度 plot 标签由原始细粒度 plot 标签派生」。默认进入价值模板榜。 |
| 剪辑/视频基础 `cut_*` | 否 | 时长、分辨率、剪辑节奏，视频专属。 |

结论：**ScriptLens 只生产 plot 一类（6 原始 + 4 派生 = 10 维），其他四类由素材侧自行生产**。剧本侧和素材侧通过相同的 plot enum 在事后 join，不直接生产对方维度的标签。

## 5. 多标签规则

| 问题 | 决策 | 依据 |
| --- | --- | --- |
| 一个情节单元跨维度有多少标签 | 同时拥有 6 + 4 = 10 个 plot 字段 | 派生关系并列，不嵌套 |
| 单个维度内是否多选 | 默认单选 top-1 | LLM 输出稳定性优先；schema 用 `list[Literal]` 兼容未来开多选 |
| 一场是否可有多组标签 | 是。一场含 N 个 plot_unit，就有 N 组 10 元组 | 标签载体在 plot_unit，不在场 |
| 6 原始与 4 派生是嵌套展示吗 | 否。两组并列展示，business_* 默认显示，原始 6 维放在「审计/详情」折叠区 | 派生关系 ≠ 父子关系，价值模板榜口径是平铺的 |

## 6. 情节如何对应视频

剧本里没有视频文件本身，剧本侧无法直接给情节贴一个视频 URL。情节 ↔ 视频的对应分两条路径：

### 6.1 语义对齐（统计层，必须做）

通过 `drama_id` + plot enum 在两侧做 join：

```text
script.plot_unit { drama_id, scene_no, plot_unit_no, business_payoff_bucket=face_slap_counter, business_emotion_bucket=anger_humiliation, ... }
                                                                  ↓ enum 相同
video.material   { drama_id, material_id, business_payoff_bucket=face_slap_counter, business_emotion_bucket=anger_humiliation, ... }
```

落地为反查 API：「给定一个剧本情节单元的 plot 标签组合，返回相同 `drama_id` 下命中相同标签的视频素材列表 + 模板效果分」。  
预测的 dimension_template 表 `drama_rank_exp_tag_dimension_template_score`（`素材标签体系.md` §7）就是这条路径的归宿。

### 6.2 物理对齐（时间码层，可选）

「剧本第 X 场 ↔ 视频时间码 [t1, t2]」需要发行方/制作方提供的拍摄时间码元数据。ScriptLens 不做时间码识别，仅在元数据存在时直接存为关联字段。当前阶段不实现。

## 7. 自定义标签

mt 明确要求情节单元支持人工自定义标签。设计为与系统 enum 标签并存的开放标签：

```text
plot_unit
├── system_tags  10 维 enum（不可编辑，模型产出）
└── user_tags    开放字符串（可增删，按 user_id + drama_id 区分）
```

UI 上系统标签和用户自定义标签用不同色调区分。用户自定义标签不进入价值模板榜口径，仅供该用户在 ScriptLens 内部检索/筛选。

## 8. 抽取流程（两步）

### 步骤 A：场切分（确定性）

输入：剧本段落 list  
处理：正则识别 `第N集` → `X-Y 地点 时段 内/外` → 场内 △/对白/OS/VO 分类  
输出：`scene[]`，每条带 `episode_no, scene_no, location, time_of_day, in_out, characters, raw_lines[]`

此步无 LLM，纯结构化。

### 步骤 B：场内情节单元切分 + 10 维 plot 标签（LLM）

每场独立调用一次，prompt 输入：

- 场的 raw_lines
- 上下文：本场所属 episode 简介（前 N-1 场的 plot_unit summary 列表，控制 token）
- 10 维 plot enum 列表（`素材标签体系.md` §4 §5 全集）
- 输出 schema（structured output 强制）

prompt 输出 JSON：

```json
{
  "plot_units": [
    {
      "summary": "慕梦汐下跪求云逸楚杀仇人，被冷笑拒绝",
      "line_range": [1, 11],
      "plot_hook": "rescue",
      "conflict_type": "status_gap",
      "story_stage": "trigger",
      "relationship_arc": "chase_and_reject",
      "payoff_type": "none",
      "emotional_driver": "humiliation",
      "business_content_archetype": "relationship_payoff",
      "business_conflict_bucket": "relationship_power",
      "business_payoff_bucket": "none",
      "business_emotion_bucket": "anger_humiliation"
    }
  ]
}
```

稳定性约束（全部硬要求）：

1. **temperature = 0**
2. **structured output** 走 OpenAI tools / 千问 `response_format: json_schema`，所有 enum 走 `Literal[...]`，模型不能输出枚举外的值。
3. **prompt 版本号 + tag set 版本号**：每次调用记录 `prompt_ver + tag_set_ver`，缓存 key 用 `hash(scene_text) + prompt_ver + tag_set_ver`。enum 集变更必须升 tag_set_ver。
4. **重试策略**：JSON 解析失败 → 重试 1 次；enum 越界 → 自动改写为 `none` + 记录告警。
5. **业务派生 4 维的产出方式**：先尝试让 LLM 与原始 6 维一起输出，离线评测稳定性；如果稳定性不足，则切换为**规则函数从原始 6 维派生**（向 mt 拿 `data_analyze_drama_predict` 仓库里的派生函数源码做对齐）。本文档不锁死，留两条路径，evaluator 决定。

## 9. 评测口径

新建评测脚本 `ScriptLens/backend/eval/plot_tag_eval.py`：

1. 配对样本由 mt / 人工标注提供 20~50 集，每集多场，每场多 plot_unit + 10 维标签。
2. 切分一致性：模型切的 plot_unit 数 vs 人工切的 plot_unit 数，按场聚合，Spearman 相关。
3. 每维标签 Cohen's Kappa（与人工标注一致性），独立给出 10 维 + 平均值。
4. 复现稳定性：同样的 scene 文本跑 N=5 次，每维投票后的 majority-vote 一致率（不依赖人工标注）。

业务粗粒度 4 维要求平均 Kappa ≥ 0.6（中等一致）才进入榜单口径；不达标只在审计视图露出。

## 10. 数据库 schema 影响

新建两张表（替换当前 highlights 逻辑里的字段）：

```sql
-- 情节单元主表
CREATE TABLE plot_units (
  id BIGSERIAL PRIMARY KEY,
  script_id BIGINT NOT NULL REFERENCES scripts(id),
  episode_no INT NOT NULL,
  scene_no INT NOT NULL,          -- 场内序号，如 1-1 中的 1
  unit_no INT NOT NULL,           -- 场内情节单元序号
  summary TEXT NOT NULL,
  line_start INT NOT NULL,
  line_end INT NOT NULL,
  prompt_ver VARCHAR(32) NOT NULL,
  tag_set_ver VARCHAR(32) NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(script_id, episode_no, scene_no, unit_no)
);

-- 标签纵表（10 个维度 = 10 行 / plot_unit）
CREATE TABLE plot_unit_tags (
  id BIGSERIAL PRIMARY KEY,
  plot_unit_id BIGINT NOT NULL REFERENCES plot_units(id) ON DELETE CASCADE,
  dim VARCHAR(64) NOT NULL,       -- plot_hook / business_payoff_bucket / ...
  value VARCHAR(64) NOT NULL,     -- enum value
  source VARCHAR(16) NOT NULL,    -- 'llm' | 'rule_derived' | 'user'
  created_at TIMESTAMPTZ DEFAULT NOW(),
  INDEX (dim, value),
  INDEX (plot_unit_id)
);

-- 用户自定义标签
CREATE TABLE plot_unit_user_tags (
  id BIGSERIAL PRIMARY KEY,
  plot_unit_id BIGINT NOT NULL REFERENCES plot_units(id) ON DELETE CASCADE,
  user_id BIGINT NOT NULL,
  label VARCHAR(64) NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(plot_unit_id, user_id, label)
);
```

`scenes` 表保留为外层结构表，仅承载结构字段（episode_no, scene_no, location, time_of_day, in_out, characters, line_start, line_end），不再承载 plot 标签。

## 11. 与现有 highlights 实现的处置

ScriptLens 当前 highlights 是 demo，与本设计不对齐：

- 字段集不是 `素材标签体系.md` 的 enum，缺少业务派生层；
- 粒度是「场或场片段」而非情节单元；
- 没有版本号、缓存、稳定性约束。

处置：highlights 不再迭代，保留旧表数据只读，新链路完全独立，迁移完成后下线 highlights 表与 UI。前端在过渡期可同时展示「情节标签」与「旧版看点」两个 section，3 周后移除旧版。

## 12. 与前端 UI 的关系（仅记录不锁死）

`scriptlens-report-rail.tsx` 报告右栏需要：

- 一个新的「情节标签」section，按场（折叠列表）→ plot_unit（卡片）→ 每个 plot_unit 默认显示 4 维 business_* chip + 一个「详情」按钮（展开 6 维原始 chip）。
- 每个 enum chip 右侧一个电影 icon 按钮，点击触发反查 API（§6.1），跳到带 plot enum 筛选的视频素材榜。
- 每个 plot_unit 卡片右下角「+ 添加标签」按钮，弹出输入框，写入 `plot_unit_user_tags`。

详细交互在 UI 实现时另起 PR 设计文档，不在本决策范围。

## 13. 不做什么

为避免再次扩张范围，明确以下事项**当前不做**：

1. 不从剧本反推 `drama_tags`。
2. 不在剧本侧生成任何 visual / asr / cut 维度的标签。
3. 不做剧本场 ↔ 视频时间码对齐。
4. 不为每个 enum 维度做多选（默认单选 top-1）。
5. 不沿用 highlights 逻辑做兼容层（新表新链路，旧表只读）。
