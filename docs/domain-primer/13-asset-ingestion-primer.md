# 资产入库扫盲：为什么“角色”可以跨剧本复用

> 一句话结论：**跨剧本复用的不是“剧情角色实例”，而是“可生产的角色资产主体（asset identity）”。**

---

## 1) 先把两个“角色”拆开

| 层 | 对象 | 生命周期 | 是否跨剧本 |
|---|---|---|---|
| 剧本层（叙事） | 某剧本里的角色实例（在这部戏里做了什么） | 跟剧本绑定 | 通常不跨 |
| 资产层（生产） | 可复用主体资产（脸/服装风格/声线/提示词包/LoRA 等） | 跟内容生产体系绑定 | 可以跨 |

如果把这两个层混在一起，就会得到错误结论：“每个剧本一个角色，所以不能复用”。  
真正工程上复用的是**资产主体**，不是把不同剧本强行当同一个剧情人物。

---

## 2) 为什么团队要做“资产入库”

核心不是“好看”，而是**稳定性 + 成本 + 速度**。

```text
不入库（每次临时抽取）
  -> 每条流程都重新识别角色
  -> 同名不同脸 / 同脸不同名
  -> 下游分镜、头像、视频各自维护一份“角色定义”
  -> 返工成本高

入库（有稳定 asset_id）
  -> 角色主体被唯一标识
  -> 下游都引用同一 asset_id
  -> 改剧本文本不影响主体一致性
  -> 可复用、可追踪、可计费
```

在你给出的团队架构里，这正好对应：

- 剧本解析负责“识别候选角色”
- MCP 网关负责编排调用
- 资产库服务负责“主体沉淀与复用”
- 分镜/头像/视频等下游消费 `asset_id`

---

## 3) “同一角色跨剧本复用”到底指什么

### 正确理解

同一 IP 或同一人物设定在多个剧本版本中出现时，复用同一个 `asset_id`：

- 原剧本
- 改写版（rewrite 后）
- 海外版/审核版
- 第二季/番外

**文本会变，主体不一定变**。  
所以资产层需要稳定 ID，避免每次重建。

### 错误理解

“A 剧有个叫小雨，B 剧也有个叫小雨，所以直接复用” -> 这是误合并，必须避免。

---

## 4) 什么时候复用，什么时候禁止复用

```text
发现一个新角色候选
   |
   |-- 是否已有候选资产（名称/别名/设定相似）?
   |       |
   |       |-- 否 -> 新建 asset_id
   |       |
   |       |-- 是 -> 置信度是否达到阈值?
   |                 |
   |                 |-- 否 -> 人工确认后再绑定
   |                 |
   |                 |-- 是 -> 绑定已有 asset_id
```

最小规则（MVP 可执行）：

1. **默认不复用**：新角色先当新主体候选  
2. **高置信才自动复用**：名称 + 别名 + 设定特征要同时命中  
3. **低置信必须人工确认**：宁可多建，不要错并  
4. **可回滚**：绑定关系必须能解除并重绑

## 5) 映射到你当前 ScriptLens MVP

你现在的存储不是“纯 JSON”，而是**结构化表 + JSONB**：

- `scripts`：剧本元数据
- `scenes`：场景原文与 `characters[]`
- `reports.report_json`：报告聚合 JSONB
- `script_operations`：改写快照（before/after）

这意味着你已经有“角色候选信号”，但还没有“资产绑定层”。

可直接利用的候选信号：

- `scenes.characters[]`（场级出现）
- `character_graph.nodes`（角色画像）
- `extract_characters_tool` 聚合结果（首场、场次统计）

## 6) 资产入库的最小落地模型（建议）

新增一层“绑定关系”，而不是改动现有解析主存储：

| 表/对象 | 作用 | 关键字段 |
|---|---|---|
| `asset-library-backend` 的角色资产 | 主体真身 | `asset_id`, `canonical_name`, `aliases`, `profile` |
| 本地映射 `script_asset_links`（建议） | 剧本角色候选 -> 资产 | `script_id`, `scene_id`, `character_name`, `asset_id`, `confidence`, `status` |

状态建议：

- `proposed`：候选匹配，未确认
- `confirmed`：确认绑定
- `rejected`：确认不绑定

这样做的好处：

- 不破坏你现有 `scripts/scenes/reports` 主链路
- 可以渐进上线（先人工确认，再自动化）
- 对接下游时直接给 `asset_id`

---

## 7) 反例 vs 正例

### 反例（常见坑）

- 只按名字匹配，导致同名角色被合并
- 把“剧本角色”当“资产主体”，改写后 ID 漂移
- 绑定后不可撤销，错了只能手改数据库

### 正例（推荐）

- 剧本层保留局部角色语义，资产层维护稳定主体 ID
- 匹配有置信度和人工确认门
- 绑定是事件化、可审计、可回滚
