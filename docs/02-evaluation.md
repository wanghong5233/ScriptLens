# ScriptLens 评估方法

## 1. 评估目标

ScriptLens 的价值不是"生成一份看起来完整的报告",而是帮助用户更快、更准地判断一份陌生长剧本。

评估要回答五个问题:

- 分析是否准确。
- 是否遗漏影响判断的关键信息。
- 是否能帮助用户节省阅读时间。
- 是否能稳定处理不同类型文本。
- 改写是否真的改善低分问题。

## 2. 评估对象

评估覆盖完整 Agent 链路,不是只测模型输出:

- 解析结果:结构化报告是否覆盖关键字段。
- 证据定位:判断是否能回到原文。
- 多轮问答:追问是否基于剧本回答。
- 视角切换:不同岗位视角是否改变信息优先级。
- 数据分析:评分是否有依据。
- 改写能力:改写是否解决目标问题。
- 反馈迭代:用户反馈是否影响后续结果。

## 3. 测试集设计

### 3.1 样本来源

第一阶段使用 5-8 个小型样本即可:

- 1 个已知样本:`samples/xiaoqie.txt`。
- 2 个不同题材网文/短剧样本:现代言情、悬疑/逆袭。
- 1 个标准剧本格式样本:含场景、角色、对白。
- 1 个低质量样本:节奏拖、动机弱、冲突弱。
- 1 个高风险样本:含暴力、伦理、敏感表达或审核风险。
- 1 个长文本样本:验证分段、聚合和追问稳定性。

### 3.2 人工标注

每个样本至少标注:

- `core_plot`:核心主线。
- `main_characters`:主要人物及关系。
- `key_conflicts`:关键冲突。
- `hooks`:钩子、爽点、反转、传播点。
- `risks`:逻辑、节奏、动机、审核、市场风险。
- `must_read_spans`:必须定位的关键原文段落。
- `decision`:推荐继续看 / 谨慎继续 / 不建议继续。
- `rewrite_targets`:可改写的低分段落及目标。

标注不是追求文学评论完整性,而是建立评估锚点:哪些信息一旦错了,会影响用户判断。

## 4. 核心指标

### 4.1 覆盖率

衡量系统是否找到了关键信息。

- `plot_coverage`:核心主线是否覆盖。
- `character_coverage`:主要人物和关系是否覆盖。
- `conflict_coverage`:关键冲突是否覆盖。
- `hook_coverage`:钩子、爽点、反转是否覆盖。
- `risk_coverage`:明显问题和风险是否覆盖。

评分方式:

- 0:遗漏或错误。
- 1:提到但模糊。
- 2:准确覆盖。

### 4.2 准确性

衡量系统是否歪曲原文。

- 人物关系是否正确。
- 因果链是否正确。
- 反转和结局是否正确。
- 对角色动机的解释是否有原文支撑。
- 风险判断是否过度推断。

评分方式:

- 0:关键错误。
- 1:小错误但不影响大判断。
- 2:准确。

### 4.3 证据可信度

衡量结论是否可验证。

- 核心结论是否绑定原文片段。
- 证据是否支持结论。
- 证据粒度是否可读。
- 是否存在"结论正确但证据不相关"。

评分方式:

- 0:没有证据或证据错误。
- 1:有证据但不够直接。
- 2:证据直接支撑判断。

### 4.4 决策帮助度

衡量报告是否真正帮助用户判断。

- 是否给出明确建议。
- 是否说明继续看的理由。
- 是否说明不继续看的风险。
- 是否指出优先阅读位置。
- 是否区分不同岗位关注点。

评分方式:

- 0:只有摘要,不能决策。
- 1:有建议但理由薄弱。
- 2:建议清晰,理由和证据完整。

### 4.5 时间节省

衡量用户是否更快建立有效认知。

测试方法:

- 对同一剧本,记录人工完整阅读估算时间。
- 记录用户使用 ScriptLens 后形成初步判断的时间。
- 记录用户定位关键段落的时间。

目标:

- 30 秒内得到继续/谨慎/不建议的初步判断。
- 3 分钟内理解主线、人物、看点、风险。
- 10 分钟内完成可讨论的 coverage 级认知。

### 4.6 稳定性

衡量不同输入形态下是否稳定:

- 标准剧本。
- 网文体。
- 短剧分集。
- 未整理长文本。
- 章节编号混乱文本。
- 含大量噪音的文本。

失败标准:

- 报告字段缺失。
- 原文定位失效。
- 大段幻觉。
- 评分无依据。
- 多轮问答脱离剧本。

## 5. 改写评估

改写评估不看"文笔是否更漂亮",而看是否解决目标问题。

每个改写任务必须先声明:

- 目标问题:例如开篇不抓人、动机弱、冲突弱、节奏拖。
- 改写策略:提前冲突、补动机、删铺垫、强化反转。
- 保留约束:人物关系、事实设定、世界观、关键结局。
- 预期改善维度:节奏、冲突、清晰度、爽点、可传播性。

评分维度:

- `problem_fit`:是否针对目标问题。
- `story_consistency`:是否保留原剧情约束。
- `improvement`:是否比原文更能达成目标。
- `specificity`:是否给出具体改动,不是泛泛建议。

低评级触发规则:

- 任一核心维度小于 60/100,推荐给优化建议。
- 开篇吸引力小于 60/100,优先给开篇改写。
- 人物动机小于 60/100,优先补动机。
- 节奏小于 60/100,优先做压缩和节点前置。

## 6. LLM-as-Judge 设计

LLM-as-Judge 只做辅助评估,不能替代人工标注。

Judge 输入:

- 原文片段。
- 人工标注。
- Agent 输出。
- 待评估维度。

Judge 输出:

- `score`:0-2 或 0-100。
- `reason`:简短理由。
- `evidence`:引用原文或标注。
- `failure_type`:遗漏 / 幻觉 / 证据不足 / 过度推断 / 格式错误。

Judge 约束:

- 不允许依据常识脑补剧情。
- 判断必须基于原文和标注。
- 如果输出没有证据,证据可信度不得高分。
- 如果结论正确但原因错误,准确性不能满分。

## 7. 可运行评估脚本设计

D3-D10 实现阶段需要提供:

```bash
make eval
```

预期流程:

1. 读取 `eval/fixtures/*.txt`。
2. 读取 `eval/golden/*.json`。
3. 调用 ScriptLens 分析链路生成 `eval/runs/{run_id}/*.json`。
4. 对结构完整性做程序化检查。
5. 对覆盖率、准确性、证据可信度调用 judge。
6. 输出 `eval/runs/{run_id}/report.md`。

报告至少包含:

- 总分。
- 各样本得分。
- 各维度得分。
- 失败样例。
- 与上一轮结果对比。
- 是否达到 release gate。

## 8. Release Gate

进入最终 demo 前,最低要求:

- 结构化报告字段完整率 >= 95%。
- 核心主线准确率 >= 80%。
- 主要人物覆盖率 >= 80%。
- 关键冲突覆盖率 >= 75%。
- 证据可信度 >= 75%。
- 多轮问答 10 个标准问题中至少 8 个有证据回答。
- 改写任务 5 个样本中至少 4 个能明确改善目标问题。
- 线上 demo 使用样本剧本完整跑通。

如果指标不达标,优先修复:

1. 原文证据定位。
2. 核心主线和人物关系。
3. 决策建议。
4. 评分依据。
5. 改写体验。

## 9. 人工验收脚本

最终展示时按以下路径验收:

1. 上传 `samples/xiaoqie.txt`。
2. 等待生成报告。
3. 30 秒内查看结论卡片。
4. 切换到选品视角,看是否值得继续推进。
5. 点击"关键反转",跳到原文证据。
6. 追问"陆寻为什么赶走秀秀?"。
7. 切换到投放视角,查看可切片爽点。
8. 查看评分低项和优化建议。
9. 触发一段改写。
10. 提交反馈"这个故事更像网文短篇不是标准剧本",查看后续分析是否调整。

这条路径覆盖基础要求和全部加分项。
