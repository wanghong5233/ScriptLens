# dcccloud 项目架构认知

## 范围

纳入公司既有项目架构判断的仓库：

- `RavenWeb`
- `cinegen-mcp`
- `storyboard_agent`
- `data_analyze_drama_predict`
- `drama_cut`
- `litellm`

不纳入公司既有项目架构：

- `ScriptLens`：本地 MVP / 联调后端，用于验证剧本解析能力接入 `RavenWeb`。

## 顶层结论

`RavenWeb` 是当前关键消费端。它基于 LobeHub fork，承载 Raven 项目工作台、资产看板、分镜、视频生成和项目协作链路。

`RavenWeb` 的主业务链路是前端通过 `lambdaClient` / tRPC 调用 `src/server/routers/lambda/*`，再由 server 侧 router 调用 Zou、Seedance Asset Library、Billing Gateway、模型运行时等外部服务。

`cinegen-mcp` 是 CineGen DSL / 项目上下文 / 媒体生成 MCP 服务，当前入口是 stdio MCP server，可被 MCP client / Agent 运行时消费。当前代码不能证明 `RavenWeb` 的主业务链路固定经过 `cinegen-mcp`。

更稳妥的理解：

```text
[链路 A] RavenWeb tRPC BFF
  RavenWeb 前端
    ↓ lambdaClient / tRPC
  RavenWeb server lambda routers
    ↓ server-side HTTP / SDK / DB / model runtime
  Zou、Seedance Asset Library、Billing Gateway、LiteLLM、模型供应商

[链路 B] MCP 工具链路
  MCP client / Agent 运行时
    ↓ stdio
  cinegen-mcp server
    ↓ DSL / 项目上下文 / 媒体生成工具
  PostgreSQL MCP 上下文表、LiteLLM、模型供应商、TOS / 资产上传能力
```

`RavenWeb` 与 `cinegen-mcp` 当前不是已实装的固定上下游关系。它们是两条已经存在的能力链路；未来是否合流，要看正式契约设计和产品接入方案。

Python 仓库不是全部业务后端。`RavenWeb` 和 `cinegen-mcp` 都是 TypeScript，且包含业务编排逻辑。`storyboard_agent`、`data_analyze_drama_predict`、`drama_cut` 是独立能力仓库。

部署形态不能统一概括为同一种 Serverless + NAS 模型。当前可见形态包括 Next.js / SPA、tRPC BFF、stdio MCP、FastMCP、火山 veFaaS、APIG、TOS 挂载、本地 Docker dev 服务等。

## 本地开发运行形态

当前本地 RavenWeb 开发态不是 Docker 服务。

`RavenWeb` 执行 `pnpm dev` 后，由 `scripts/devStartupSequence.mts` 启动两个 Node.js 开发服务：

```text
localhost:3010
  Next.js dev server
  承载页面、Next runtime、tRPC / server-side BFF 逻辑

localhost:9876
  Vite SPA dev server
  承载 SPA 开发构建与热更新链路
```

因此，本地访问 `http://localhost:3010/workspace` 时，跑在本机的是 RavenWeb 的 Web/BFF 核心代码；它不是一个纯静态前端，也不是 Docker 容器。

RavenWeb 是否需要 Docker 取决于依赖怎么配置：

- 如果 `.env.development.local` 指向云端 PostgreSQL、Redis、Zou、Billing Gateway 等服务，本地只需要启动 Node.js dev server，Docker Desktop 不需要开启。
- 如果要完整本地化基础设施，可使用 `pnpm dev:docker` 启动仓库里的 Docker Compose dev 依赖，包括 PostgreSQL、Redis、RustFS、Searxng。
- `pnpm dev:docker` 启动的是基础设施依赖，不等于 RavenWeb Web 进程本身跑在 Docker 里。

当前更准确的本地心智模型：

```text
浏览器
  ↓ localhost:3010
RavenWeb 本地 Node.js dev server
  ↓ server-side env / tRPC / service clients
远端或本地依赖服务
  PostgreSQL / Redis / Zou / Billing Gateway / Seedance Asset Library
```

## RavenWeb

`RavenWeb` 使用 LobeHub 作为底座，Raven 业务入口集中在自定义项目工作台和 lambda routers。

关键前端位置：

- `RavenWeb/src/routes/(main)/projects/[id]/index.tsx`
- `RavenWeb/src/components/raven/*`
- `RavenWeb/src/components/raven/batch-storyboard-creator.tsx`
- `RavenWeb/src/components/raven/kanban/*`

关键服务端位置：

- `RavenWeb/src/server/routers/lambda/index.ts`
- `RavenWeb/src/server/routers/lambda/zou.ts`
- `RavenWeb/src/server/routers/lambda/video/index.ts`
- `RavenWeb/src/server/routers/lambda/billing.ts`
- `RavenWeb/src/server/services/zou/client.ts`
- `RavenWeb/src/server/services/billing/index.ts`
- `RavenWeb/src/server/services/cinegen/seedanceAssetRegistration.ts`
- `RavenWeb/src/server/modules/ModelRuntime/index.ts`
- `RavenWeb/src/envs/zou.ts`
- `RavenWeb/src/envs/cinegen.ts`
- `RavenWeb/src/envs/llm.ts`
- `RavenWeb/src/envs/gateway.ts`

RavenWeb 的业务事实：

- `/projects/[id]` 是 Raven 项目工作台。
- 项目、资产、任务、预览版本主要通过 `zou` tRPC router 管理。
- 视频生成通过 `video` router 创建异步任务并调用模型运行时。
- Seedance oversea 支持 `asset://` 引用和主体库注册。
- `billing` router 已实装账户余额查询，通过 `BillingGatewayService` 调用 Billing Gateway。
- OpenAI 或非内置/custom provider 的模型请求会在 `ModelRuntime` 中进入 Billing Gateway；其他内置 provider 是否进入 Billing Gateway 由 `shouldUseBillingGateway` 判断，不能概括成所有模型请求一律经过 Billing Gateway。

## RavenWeb 外部 HTTP 服务接入模式

仓库中已经存在可复用的外部 HTTP 服务集成模板：Zou。

Zou 是独立 HTTP 后端，RavenWeb 不通过 `cinegen-mcp` 调用它，而是通过 tRPC BFF 直接在 server 侧封装 HTTP client。

标准三层结构：

| 层 | 文件 | 作用 |
|---|---|---|
| env 配置 | `src/envs/<service>.ts` | 用 `@t3-oss/env-core` + `zod` 声明并校验服务端环境变量 |
| server HTTP client | `src/server/services/<service>/client.ts` | 封装 fetch / undici，集中处理 base URL、鉴权、错误和返回类型 |
| lambda router | `src/server/routers/lambda/<service>.ts` | 暴露 tRPC procedure 给 SPA 调用，并在 `lambda/index.ts` 注册 |

ScriptLens 这类本地独立 HTTP 后端接入 RavenWeb 时，应优先沿用这套模式，不需要为 walking skeleton 设计新架构。

## cinegen-mcp

`cinegen-mcp` 的核心职责是围绕 CineGen 项目 DSL 提供 MCP 工具，运行形态为 stdio MCP server。

关键位置：

- `cinegen-mcp/src/server.ts`
- `cinegen-mcp/src/context/*`
- `cinegen-mcp/src/schema/*`
- `cinegen-mcp/src/storage/*`
- `cinegen-mcp/src/image-generator.ts`
- `cinegen-mcp/src/video-generator.ts`
- `cinegen-mcp/src/voice-generator.ts`
- `cinegen-mcp/src/image-stitcher.ts`
- `cinegen-mcp/src/asset-uploader.ts`

工具分组：

- 上下文工具：`context_sync`、`context_snapshot`、`context_impact`、`context_mutate`、`context_deps`
- 图像工具：`generate_images`、`modify_image`
- 视频工具：`generate_video`、`remove_subtitle`
- 音频工具：`generate_voice`
- 辅助工具：`stitch_images`、`register_character_identity`

设计事实：

- MCP 拥有自己的上下文存储表。
- 业务系统通过 `context_sync` 把项目 DSL 同步进 MCP。
- Agent 读取业务摘要，不必直接依赖完整 DSL 结构。
- 变更通过 `context_mutate` 合并回 DSL。
- 依赖和影响分析由 MCP 服务计算。
- 当前代码没有显示它已经处在 RavenWeb tRPC 主链路中。

## litellm

`litellm` 是模型网关 fork。

RavenWeb 中和 LiteLLM / Billing Gateway 相关的事实：

- `RavenWeb/src/utils/billingGateway.ts`：解析 Billing Gateway URL。

## ScriptLens 接入边界

`ScriptLens` 当前只承担本地 MVP / 联调后端角色，不属于公司既有架构。

物理事实：

- 直接运行 `backend/app/app_main.py` 时，默认端口是 `8000`。
- Docker dev / Makefile 联调端口是 `8005`，以 `backend/docker-compose.dev.yml` 和 `backend/Makefile` 为准。
- Docker dev 暴露 `scriptlens_api` 到宿主机 `http://localhost:8005`。
- Docker dev 会同时拉起 ScriptLens 自己隔离的 PostgreSQL / Redis / API 容器，适合作为 RavenWeb 本地联调的稳定后端形态。
- 使用 Docker dev 前必须先启动 Docker Desktop；否则 `docker compose` 无法连接 Docker daemon。
- `/health` 是公开健康检查。
- `/api/scripts` 依赖 `get_current_user`，需要 JWT。
- `SM_DEMO_MODE=true` 不等于所有业务 API 免鉴权；它会禁用注册等 demo 行为，但不会让 `/api/scripts` 跳过 JWT。
- `SM_DEMO_ENTRY_ENABLED=true` 时，可以通过 `/api/users/demo-entry` 获取 demo token，前提是数据库中存在可用的 `SM_DEMO_USERNAME` 用户。
- 未发现 `X-Demo-User` 这类 header 鉴权路径。
- CORS 由 `SM_CORS_ALLOW_ORIGINS` 控制；RavenWeb 本地 dev 常见端口需要加入 `3010` 和 `9876`。

当前阶段目标是 walking skeleton：

```text
RavenWeb 前端
  ↓ scriptLensDev tRPC procedure
RavenWeb server scriptlens-dev client
  ↓ fetch
ScriptLens 本地后端（优先 Docker dev）
  - Docker dev: http://localhost:8005
  - 直接运行 app_main.py: http://localhost:8000
  ↓
返回原样 JSON
  ↓
RavenWeb 页面展示
```

当前联调推荐使用 Docker dev 跑 ScriptLens，因为它提供固定端口、隔离数据库、隔离 Redis 和接近服务化部署的运行边界。RavenWeb 不需要和 ScriptLens 共用进程、共用依赖或共用数据库。

后续如果进入正式集成，应复用的是这个服务边界：

```text
RavenWeb Node.js BFF
  ↓ server-side HTTP client
ScriptLens 能力服务
```

本地 Docker 只是开发部署形态，不是正式架构约束。正式环境可以是容器、云服务、APIG 后端、内部服务或未来 MCP tool；只要 RavenWeb 通过明确的 server-side 服务边界调用即可。

当前阶段不做：

- 不设计最终接口契约。
- 不接下游消费。
- 不写入 Zou 数据模型。
- 不注册 `cinegen-mcp`。
- 不接 `storyboard_agent`。
- 不把 `ScriptLens` 写入公司既有架构。

当前阶段只做：

- 沿用 RavenWeb 外部 HTTP 服务接入的三层标准模式。
- 命名空间统一加 `dev` 后缀，与正式契约物理隔离。
- 先调用 `/health` 跑通 RavenWeb 本地 Node.js BFF → ScriptLens Docker dev 后端的物理链路。
- 如需调用 `/api/scripts`，先通过 demo-entry 或 login 获取 JWT，再带 `Authorization: Bearer <token>` 调用。
- 返回值类型保持 `unknown`，不声明业务字段为最终契约。
- 团队提供的模型环境变量可以填入 ScriptLens 本地 `.env.dev`，但只填必要变量，不复制无关密钥，不提交 `.env.dev`。

隔离规则：

| 规则 | 做法 |
|---|---|
| 命名 | 文件夹 `scriptlens-dev/`、tRPC namespace `scriptLensDev.*`、env 变量 `SCRIPTLENS_DEV_*` |
| 注释 | 临时文件顶部标注 `DEV-ONLY: temp integration, contract NOT stable` |
| 类型 | 返回值用 `unknown`，不为业务字段声明最终 schema |
| Agent / Plugin | 不注册成 LobeHub Function Call tool / 插件 |
| 持久化 | 不写入 RavenWeb 自有 PG / Redis |

## 下一步

1. 启动 ScriptLens 后端。
2. 本地联调优先用 Docker dev：先启动 Docker Desktop，再在 `ScriptLens/backend` 执行 `make up-build` 或 `docker compose -f docker-compose.dev.yml up -d --build`，验证 `http://localhost:8005/health`。
3. 如果不用 Docker，直接运行 `app_main.py`，验证 `http://localhost:8000/health`。
4. 在 ScriptLens `.env.dev` 设置必要的团队模型环境变量、`JWT_SECRET_KEY`、`SM_CORS_ALLOW_ORIGINS=http://localhost:3010,http://localhost:9876,http://localhost:5173,http://localhost:3000`，并确认 `SM_DEMO_ENTRY_ENABLED=true`。
5. RavenWeb 已通过 `pnpm dev` 在本地 Node.js dev server 跑起来，入口是 `http://localhost:3010/workspace`。
6. 在 RavenWeb `.env.development.local` 设置 `SCRIPTLENS_DEV_BASE_URL=http://localhost:8005`；如果直接运行 ScriptLens，则改为 `http://localhost:8000`。
7. 按 Zou 模板新增 RavenWeb 临时接入层：
   - `src/envs/scriptlens.ts`
   - `src/server/services/scriptlens-dev/client.ts`
   - `src/server/routers/lambda/scriptLensDev.ts`
   - 在 `src/server/routers/lambda/index.ts` 注册 `scriptLensDev`
8. 第一刀只接 `health`，确认 RavenWeb 页面能展示 ScriptLens `/health` 返回 JSON。
9. 第二刀再接一个业务方法；业务方法不要使用 `X-Demo-User`，应先获取 demo token 或 login token。
10. 演示 walking skeleton 后，再进入正式化讨论：v3 标签 schema、接口契约稳定化、数据落库、MCP 注册、Zou 任务、下游消费。
