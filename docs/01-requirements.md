# ScriptLens 需求拆解

## 1. 唯一需求源

本项目以 `docs/source/task.md` 为唯一最高需求源。所有功能、架构、评估、展示和交付材料,都必须服务一个核心问题:

> 用户面对一份较长、未经整理的剧本时,如何在尽可能短的时间内,尽可能准确地理解这份剧本,并判断它是否值得继续投入时间。

这里的"理解"不是压缩文本,也不是剧情简介,而是把长文本中影响判断的信息提取、组织、定位、解释出来。

## 2. 问题本质

用户表面上缺时间,本质上缺的是"可验证的判断依据"。

用户不能只看摘要,因为摘要通常只回答"讲了什么",但真实工作判断还需要回答:

- 主线是否清楚。
- 人物关系和冲突是否成立。
- 钩子、反转、爽点是否足够集中。
- 前半段是否能抓住用户。
- 角色动机是否能支撑关键行为。
- 作品最值得关注的价值是什么。
- 存在哪些明显问题和推进风险。
- 是否值得继续看、讨论、购买、投放或改稿。

因此 ScriptLens 的目标不是把文本变短,而是让用户更快形成可靠判断。

## 3. 用户场景

题目给出的用户不是单一角色,而是内容产业链中会接触陌生剧本的人:

- 内容策划:关心故事设定、人物关系、可开发空间。
- 编剧统筹:关心结构、动机、冲突、节奏、改写空间。
- 内容运营:关心卖点、标签、受众、传播钩子。
- 选品人员:关心是否值得继续读、是否值得推进、风险在哪里。
- 投放人员:关心前几集抓人程度、爽点密度、短视频切片点。
- 审核人员:关心敏感内容、价值观风险、理解障碍。

产品不能把这些角色做成互相割裂的系统,但必须支持视角切换。默认报告解决"快速判断",视角报告解决"不同岗位关注点"。

## 4. 必须回答的用户问题

### 4.1 快速决策问题

- 这部剧是否值得继续看?
- 它最大的价值是什么?
- 它最大的风险是什么?
- 用户应该优先看哪些段落?
- 如果只能花 3 分钟,应该先看什么?

### 4.2 内容理解问题

- 核心主线是什么?
- 关键人物是谁,彼此关系如何?
- 主要冲突如何发生、升级、解决?
- 关键反转在哪里?
- 人物动机是否自洽?
- 前半段是否抓人?

### 4.3 价值判断问题

- 卖点、爽点、情绪钩子在哪里?
- 哪些桥段具有传播潜力?
- 题材、设定、人物关系是否有市场识别度?
- 剧本质量、可读性、结构完整度、节奏表现如何?

### 4.4 风险识别问题

- 是否存在明显逻辑断裂?
- 是否存在角色动机缺失?
- 是否存在节奏拖沓或信息噪音过多?
- 是否存在低俗、暴力、伦理、版权或审核风险?
- 哪些结论置信度不足,需要人工复核?

### 4.5 交互追问问题

- 某个判断的原文依据是什么?
- 某个人物为什么这么做?
- 某段剧情是否可以改得更抓人?
- 如果我是投放/编剧/审核视角,应该看哪些点?
- 用户指出分析不准后,系统如何修正当前结果?

## 5. 功能需求

### 5.1 输入剧本

必须支持上传或粘贴长文本。输入文本可能是标准剧本、短剧分集稿、网文片段、未整理小说、混合格式文档。

边界要求:

- 不假设输入一定有标准场景号。
- 不假设输入一定有角色对白格式。
- 不假设文本干净,需要处理空行、编号、版权信息、简介、章节标题等低价值文本。

### 5.2 结构化分析

系统必须生成结构化报告,而不是自由散文。报告至少包括:

- 一句话判断:推荐继续看 / 谨慎继续 / 不建议投入。
- 核心主线:用简洁语言说明故事推动力。
- 人物关系:主要人物、关系、冲突、动机。
- 冲突与反转:关键冲突、升级节点、反转位置。
- 看点与卖点:钩子、爽点、传播点、情绪价值。
- 节奏分析:开篇吸引力、信息密度、拖沓点、高潮分布。
- 风险与问题:逻辑、动机、节奏、审核、市场风险。
- 重点定位:值得优先阅读的原文段落。
- 综合评分:质量、节奏、人物、商业潜力、风险等维度。

### 5.3 原文依据

关键判断必须能回到原文。用户不能只看到结论,还要能查看支持这个结论的片段。

依据粒度:

- 段落级定位是 MVP 底线。
- 有章节/场景号时,优先使用章节/场景定位。
- 前端展示中,点击结论应能跳到左侧原文证据。

### 5.4 分层呈现

系统要满足不同时间预算:

- 30 秒:结论卡片,告诉用户是否值得继续看。
- 3 分钟:主线、人物、看点、风险、评分。
- 10 分钟:完整 coverage report + 证据片段 + 视角报告。
- 深入阅读:原文定位、多轮追问、改写建议。

### 5.5 多视角查看

必须支持不同角色的关注点:

- 选品/推进视角:是否值得继续投入。
- 编剧/策划视角:结构、动机、冲突、改写空间。
- 运营/投放视角:钩子、爽点、传播切片。
- 审核/风控视角:敏感内容、理解风险、价值观风险。

视角切换不是重新生成互不相关的报告,而是在同一份解析底座上重排信息优先级。

### 5.6 多轮交互

Agent 必须支持围绕剧本继续追问:

- 问剧情:回答并引用原文。
- 问人物:解释动机、关系和变化。
- 问看点:指出具体段落和可传播表达。
- 问问题:指出风险并说明影响。
- 问改写:给出可操作建议或直接改写片段。

### 5.7 迭代修正

用户可以指出分析不准、遗漏、偏好变化或新增视角。系统必须能把反馈用于当前剧本的后续分析。

MVP 版本不要求真正训练模型,但要有可见机制:

- 记录用户反馈。
- 标记哪些结论被修正。
- 支持新增临时分析视角。
- 后续追问和报告刷新时使用该反馈。

## 6. 加分项需求

### 6.1 可部署、可访问

必须有线上可访问 demo。只提供本地运行说明不够强。部署目标是让评估方能直接上传样本、查看报告、追问、体验改写。

### 6.2 评估方法

必须说明如何评估解析质量,包括:

- 解析是否准确。
- 是否遗漏关键信息。
- 是否帮助用户更快做判断。
- 是否稳定处理不同类型剧本。
- 改写是否真的改善目标问题。

评估方法本身要可执行,不能只写理念。

### 6.3 数据分析能力

系统要给出量化或等级判断,但必须说明依据。建议评分维度:

- 主线清晰度。
- 人物动机可信度。
- 冲突强度。
- 钩子/爽点密度。
- 节奏控制。
- 商业/传播潜力。
- 风险等级。

### 6.4 低评级改写

当某些维度评分较低时,系统应能给出优化建议或直接改写。

改写不能只做文风润色,必须围绕目标问题:

- 开篇不抓人:重写开场钩子。
- 动机不成立:补足行为动因。
- 冲突弱:强化选择压力和代价。
- 节奏拖:删减重复信息,提前关键事件。
- 爽点不足:增强情绪回报和反转。

### 6.5 可进化 skill 机制

系统要表现出能力可进化:

- 用户可新增分析视角。
- 用户反馈可影响后续分析。
- 常用分析模板可沉淀为 skill。
- skill 能被当前剧本调用,并在 UI 中可见。

MVP 不做复杂训练,以"可配置技能 + 用户反馈驱动模板更新"实现。

### 6.6 前端展示

前端不是加壳,而是理解效率工具。关键展示:

- 左右布局:左原文,右报告/追问。
- 结论卡片:快速决策。
- 分数雷达/条形图:量化比较。
- 时间线/剧情节点:理解主线。
- 人物关系图:理解冲突。
- 证据高亮:验证判断。
- 视角切换:不同角色不同优先级。

## 7. 非目标

以下内容不是 D1-D10 的重点:

- 不做完整影视制作管理系统。
- 不做专业票房预测模型训练。
- 不做真实市场数据库对标。
- 不做复杂版权审核系统。
- 不做多用户协作权限体系。
- 不做与旧项目架构的绑定复用。

这些能力可以作为未来扩展,但不能挤占当前考核交付。

## 8. 验收清单

基础验收:

- 用户可以输入一份长剧本。
- 系统可以输出结构化分析结果。
- 用户可以继续追问。
- 用户可以查看关键判断依据。
- 用户可以切换分析视角。
- 用户可以对结果反馈并触发修正。
- 项目可以被评估方实际体验。

加分验收:

- 有线上 demo。
- 有评估文档和可运行 eval 脚本设计。
- 有量化评分和评分依据。
- 有低分项改写能力。
- 有可进化 skill 的可见路径。
- 有服务真实使用场景的前端展示。

材料验收:

- README 说明问题理解、核心需求、使用方式和边界。
- Demo 展示从上传到报告、追问、证据、改写、反馈的完整链路。
- 文档说明取舍:为什么不是普通摘要,为什么这样设计输出结构,在哪些情况下可能失效。
