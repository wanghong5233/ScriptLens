# ScriptLens 方案调研

## 1. 技术问题定义

ScriptLens 不是普通文本摘要,技术上要解决的是:

- 长文本输入不稳定:标准剧本、短剧分集、网文、未整理文本混合存在。
- 关键信息分散:人物动机、冲突、反转、风险可能隔很远。
- 结论必须可验证:用户需要看到原文依据。
- 交互必须持续:报告之后还要追问、定位、改写和反馈。
- 评分必须可解释:不能只给一个"8.5 分"。

因此方案不能只做一次 `prompt -> summary`,而要做成"解析底座 + 报告生成 + 证据索引 + 交互 Agent + 评估回归"。

## 2. 候选路线

### 2.1 长上下文直读

做法:

- 把全文直接塞给长上下文模型。
- 一次生成完整报告。
- 追问时继续把全文或压缩后的全文传入。

优点:

- 实现最快。
- 对 10 万 tokens 以下文本可能效果不错。
- 不需要复杂索引。

问题:

- 成本高、延迟高。
- 对超长文本不稳定。
- 难以做细粒度证据定位。
- 多轮追问重复消耗上下文。
- 输出结构容易漂移。

适用位置:

- MVP 的短样本快速验证。
- 小文本的一次性 coverage 草稿。
- 作为 fallback,不是主架构。

### 2.2 分块摘要

做法:

- 把剧本切成固定长度 chunk。
- 每个 chunk 生成摘要。
- 汇总 chunk 摘要生成全局报告。

优点:

- 简单。
- 可扩展到长文本。
- 可保留 chunk id 用于粗粒度证据。

问题:

- 固定切块容易切断剧情节点。
- 局部摘要会丢失跨段因果。
- 最终报告容易成为"摘要的摘要"。
- 对人物动机、伏笔、反转等跨段信息识别弱。

适用位置:

- 做基础 ingest。
- 为后续分层抽取提供中间材料。

### 2.3 分层抽取

做法:

- 先把文本切成剧情片段。
- 对每个片段抽取结构化信息:事件、人物、冲突、情绪、钩子、风险。
- 再聚合成全局人物关系、主线、节奏和评分。

优点:

- 更接近题目要求的"提取真正有价值的信息"。
- 结构化结果可用于前端、评分、检索、改写。
- 比单纯摘要更容易做可解释评估。

问题:

- 需要设计 schema。
- 需要处理局部结论冲突。
- 聚合阶段要防止重复和幻觉。

适用位置:

- ScriptLens 主路线。
- coverage report、scorecard、timeline、character graph 的共同底座。

### 2.4 证据检索

做法:

- 为原文段落建立索引。
- 每个报告结论保存 `evidence_refs`。
- 追问时检索相关原文片段,再回答。

优点:

- 支持"查看依据"。
- 支持多轮问答。
- 降低幻觉。
- 前端可做点击定位。

问题:

- 纯向量检索可能召回相似但不支持结论的片段。
- 中文网文中代词、省略、章节跳转多,需要保留上下文窗口。
- 证据要做验证,不能只保存检索结果。

适用位置:

- 必做。
- MVP 可以先用段落级关键词 + embedding 混合检索;后续再做 rerank。

### 2.5 分层检索 / RAPTOR 思路

参考:

- RAPTOR:递归嵌入、聚类、摘要,建立树状索引,在不同抽象层级检索。
- LongRefiner:利用长文档结构做层级化压缩和查询相关精炼。

对 ScriptLens 的意义:

- 剧本理解既需要全局主线,也需要局部证据。
- 分层索引可以同时召回"整段剧情概览"和"具体原文片段"。
- 对长剧本、多章节文本有价值。

取舍:

- D1-D10 不做复杂聚类树。
- 可以实现轻量版:Document -> Act/Chapter -> Segment -> Paragraph 四层结构。
- 每层保存摘要、关键词、人物、事件和证据范围。

### 2.6 可引用摘要

参考:

- Grounded and verifiable long-form summarization 方向强调 inline citations。
- 文档摘要中的每个关键 claim 必须能追溯到 source sentence。

对 ScriptLens 的意义:

- 题目明确要求"哪些信息应该保留原文依据"。
- 评估方会对无依据判断不信任。
- 可引用输出能显著区分 ScriptLens 和普通摘要。

取舍:

- MVP 不训练专门模型。
- 用工程约束实现:每个关键结论必须带 `evidence_refs`。
- 输出后做 evidence check:没有证据的结论降置信度或不展示为强结论。

### 2.7 Agent 工具链

做法:

- Agent 不直接生成所有内容,而是调用工具:
  - `inspect_script`
  - `retrieve_evidence`
  - `generate_report`
  - `answer_question`
  - `rewrite_segment`
  - `apply_feedback`
  - `evaluate_output`

优点:

- 更符合 Agent 项目定位。
- 每个能力可观察、可测试。
- 多轮交互可持续。
- 后续 skill 机制有落点。

问题:

- 工程量高于单 prompt。
- 需要控制工具边界,避免 wrapper class 和虚假复杂度。

适用位置:

- 主产品形态。
- 但工具数量要少,每个工具必须对应真实用户问题。

## 3. 推荐路线

推荐采用:

> 语义切分 + 分层抽取 + 证据索引 + coverage report + script chat + targeted rewrite + feedback skill

流程:

1. Ingest:接收文本,清洗无效头尾信息。
2. Segment:按章节/编号/语义段切分,保留原文范围。
3. Extract:对每段抽取人物、事件、冲突、钩子、风险。
4. Aggregate:聚合主线、人物关系、节奏、看点、风险。
5. Ground:为关键结论绑定证据片段。
6. Score:按维度评分并说明依据。
7. Report:生成分层 coverage report。
8. Chat:基于证据索引回答追问。
9. Rewrite:对低分项做定向改写。
10. Feedback:记录用户反馈,更新当前剧本分析状态或新增 skill。

## 4. 输入处理策略

### 4.1 清洗

清洗目标不是改写原文,而是建立结构化视图:

- 去除明显版权声明、空白噪音。
- 保留标题、作者、分类、简介。
- 识别章节号、场景号、分集号。
- 保留原始行号和字符范围。

### 4.2 切分

优先级:

1. 显式章节/场景/分集标记。
2. 连续数字编号。
3. 语义边界:时间跳转、地点跳转、人物关系变化、冲突升级。
4. token 长度兜底。

对 `samples/xiaoqie.txt` 这类样本,数字 `1-9` 是天然剧情段落,可作为 segment。

### 4.3 元数据

每个 segment 保存:

- `segment_id`
- `title`
- `start_line`
- `end_line`
- `start_char`
- `end_char`
- `raw_text`
- `summary`
- `characters`
- `events`
- `conflicts`
- `hooks`
- `risks`
- `emotion`

## 5. 报告生成策略

报告不是从全文直接生成,而是从抽取结果生成:

- 主线来自全局事件链。
- 人物关系来自 segment 级人物互动聚合。
- 看点来自 hooks 和 emotion peaks。
- 风险来自 risk extraction 和 scorecard。
- 重点阅读来自高冲突、高反转、高风险片段。
- 决策建议来自 scorecard + risks + hooks。

这样做的原因:

- 可解释。
- 可评估。
- 可定位。
- 可复用到多视角和追问。

## 6. 问答策略

用户追问分四类:

- 定位型:"某个反转在哪?"
- 解释型:"角色为什么这么做?"
- 判断型:"这段值不值得保留?"
- 改写型:"这段怎么改更抓人?"

处理流程:

1. 识别问题类型和视角。
2. 检索相关 segment 和 evidence。
3. 读取关联人物/事件/评分。
4. 基于证据回答。
5. 返回答案、依据、置信度和建议操作。

禁止:

- 不基于原文直接编剧情。
- 对没有证据的问题强答。
- 用泛泛创作建议代替剧本内分析。

## 7. 改写策略

改写不是自动重写整部剧本,而是定向开发建议。

触发方式:

- 用户主动选择"改写这一段"。
- 某维度评分低于阈值。
- 报告指出该段存在明显问题。

改写输入:

- 原文片段。
- 目标问题。
- 保留设定。
- 期望视角:编剧、投放、选品。
- 原文前后上下文。

改写输出:

- 改写目标。
- 改写版本。
- 关键改动说明。
- 改写前后评分变化预估。
- 风险提示。

## 8. Skill 机制策略

题目要求"可进化 skill 机制",不要求训练模型。MVP 采用可解释、可演示的轻量机制:

- Skill = 分析视角 + 评分维度 + prompt 模板 + 输出字段。
- 用户反馈可生成临时 skill。
- 用户可保存常用 skill。
- 后续分析可选择 skill。

示例:

- `short_drama_hook_auditor`:专看前 3 分钟钩子和反转。
- `character_motivation_checker`:专查人物行为动机是否成立。
- `risk_review_cn_webnovel`:专查暴力、伦理、低俗、价值观风险。

## 9. 模型与框架取舍

### 9.1 后端

推荐:

- Python + FastAPI。
- Pydantic 定义输入输出契约。
- 简单任务队列先用进程内异步任务,D10 前不引入复杂消息队列。
- SQLite 或 Postgres 二选一。MVP 可用 SQLite,部署稳定后换 Postgres。

理由:

- Agent 和文本处理生态成熟。
- 类型和结构化输出容易落地。
- 部署简单。

### 9.2 前端

推荐:

- React / Next.js。
- 左右分栏:原文 + 报告/聊天。
- 图表可先使用轻量组件,避免过早引入复杂可视化。

理由:

- 最适合 demo。
- 易做证据联动。
- 方便部署。

### 9.3 LLM

推荐抽象成 provider:

- 默认支持 OpenAI-compatible API。
- 模型名走环境变量。
- prompt 和 schema 版本化。

理由:

- 不锁死具体供应商。
- 可以按成本和效果替换模型。
- 便于后续评估对比。

## 10. 风险与规避

### 10.1 做成普通摘要

规避:

- 报告字段固定。
- 每个判断有证据。
- 评分和视角必须可见。
- 多轮追问必须基于 evidence。

### 10.2 过度工程

规避:

- D1-D10 不做复杂多 Agent 编排。
- 不引入向量数据库作为硬依赖。
- 不做真实市场预测。
- 不做训练。

### 10.3 证据定位不准

规避:

- 保留 line/char span。
- 结论生成时必须选择 evidence。
- 无 evidence 的结论降级为"推测"。

### 10.4 输出漂移

规避:

- Pydantic schema。
- JSON structured output。
- eval 检查字段完整性。
- prompt 版本化。

## 11. 最终技术结论

ScriptLens 的实现不应追求"最复杂的 Agent 框架",而应追求最贴近题目的闭环:

- 用户上传长文本。
- 系统分层理解。
- 输出 coverage 级报告。
- 所有结论可回原文。
- 用户可追问、改写、反馈。
- 评估可证明效果。

这条路线能覆盖基础要求,并自然承接六个加分项。
