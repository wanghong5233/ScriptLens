# ScriptLens 加分项落地计划

## 1. 原则

加分项不是额外堆功能,而是让项目更像真实可用的 Agent 产品。

实现原则:

- 每个加分项必须在 demo 中可见。
- 每个加分项必须和题目需求相关。
- 不做超出 10 天交付能力的伪复杂功能。
- 不用概念包装替代可体验功能。

## 2. 加分项总览

必须冲刺全部 6 个加分项:

1. 可部署、可访问。
2. 提供剧本解析效果的评估方法。
3. 增加数据分析能力。
4. 对低评级剧本提供改写能力。
5. 具备可进化的 skill 机制。
6. 有适合真实使用场景的前端展示。

优先级:

1. 前端展示。
2. 评估方法。
3. 数据分析。
4. 改写能力。
5. 可部署。
6. skill 机制。

说明:

- 前端展示最影响第一印象。
- 评估方法证明不是拍脑袋。
- 数据分析和改写是题目明确加分。
- 部署必须完成,但技术风险可控。
- skill 机制要做轻量但真实可见。

## 3. 加分项 1:可部署、可访问

### 3.1 目标

评估方打开一个 URL,无需本地配置,即可体验完整链路:

- 加载示例剧本。
- 上传文本。
- 生成报告。
- 查看证据。
- 追问。
- 改写。
- 提交反馈。

### 3.2 最小可交付

- 一个线上 Web demo。
- 一个线上 API 服务。
- `.env.example` 说明配置。
- README 中提供访问链接和本地启动方式。
- 示例剧本可一键加载。

### 3.3 验收方式

打开线上地址后:

1. 点击示例剧本。
2. 生成报告。
3. 点击证据定位。
4. 追问一个问题。
5. 触发一个改写。

这五步必须跑通。

### 3.4 风险

- LLM API key 泄露。
- 云服务冷启动慢。
- 上传大文本超时。
- 数据库文件权限问题。

### 3.5 规避

- API key 只在服务端环境变量。
- 示例剧本预置,避免首次体验失败。
- MVP 限制上传大小。
- 部署前跑 smoke test。

## 4. 加分项 2:评估方法

### 4.1 目标

证明 ScriptLens 的解析质量可度量,不是只凭主观感觉。

### 4.2 最小可交付

- `docs/02-evaluation.md`。
- `eval/fixtures/` 样本集。
- `eval/golden/` 人工标注。
- `make eval` 或等价命令。
- 生成 `eval/runs/{run_id}/report.md`。

### 4.3 评估维度

- 覆盖率。
- 准确性。
- 证据可信度。
- 决策帮助度。
- 时间节省。
- 稳定性。
- 改写有效性。

### 4.4 Demo 证据

最终展示中要能看到:

- eval 命令。
- 一份评估报告。
- 指标解释。
- 失败样例。
- 下一步修复方向。

### 4.5 取舍

D10 前不追求大型评测集。小而真实的标注集比大量伪造样本更重要。

## 5. 加分项 3:数据分析能力

### 5.1 目标

除了文本解析,系统要从数据视角评价剧本质量、可读性、结构完整度、节奏和潜在表现。

### 5.2 最小可交付

Scorecard:

- 主线清晰度。
- 人物动机可信度。
- 冲突强度。
- 钩子/爽点密度。
- 节奏控制。
- 商业/传播潜力。
- 风险等级。

每个维度包含:

- 分数。
- 等级。
- 理由。
- 证据。
- 改进建议。

### 5.3 前端展示

- 总分卡。
- 维度条形图或雷达图。
- 高分项/低分项。
- 点击分数查看依据。
- 低分项可触发改写。

### 5.4 评分原则

- 评分是文本内证据驱动的相对评价。
- 不声称真实市场预测。
- 不给无依据的精确小数。
- 分数要服务决策,不是装饰。

### 5.5 Demo 证据

评估方能看到:

- `samples/xiaoqie.txt` 的评分。
- 为什么开篇钩子强。
- 为什么审核风险高。
- 为什么某维度低。
- 如何从低分项进入改写。

## 6. 加分项 4:低评级剧本改写能力

### 6.1 目标

当系统发现剧本存在低分问题时,给出具体优化建议或直接改写片段。

### 6.2 最小可交付

支持至少 5 类改写:

- 开篇钩子增强。
- 人物动机补强。
- 冲突强度增强。
- 节奏压缩。
- 风险降级/表达替换。

### 6.3 改写流程

1. 系统识别低分项。
2. 用户点击"改写这一段"。
3. 系统展示原问题和证据。
4. 用户选择改写目标。
5. 系统生成改写版本。
6. 系统解释改动点。

### 6.4 改好定义

改好不是文风变华丽,而是目标维度提升:

- 开篇更快建立冲突。
- 人物行为更有动机。
- 冲突有选择压力和代价。
- 信息更集中。
- 风险表达更可控。

### 6.5 Demo 证据

用示例剧本展示:

- 找到高风险或节奏问题片段。
- 触发改写。
- 输出改写文本。
- 对比改写前后目标维度。

## 7. 加分项 5:可进化 skill 机制

### 7.1 目标

展示 Agent 能根据用户反馈、使用过程或新增需求演化分析能力。

### 7.2 MVP 定义

Skill 不是训练出来的新模型,而是可配置的分析能力:

- 分析目标。
- 关注维度。
- 输出字段。
- prompt 片段。
- 适用场景。

### 7.3 最小可交付

内置 skill:

- 短剧钩子检查。
- 人物动机检查。
- 女频爽点分析。
- 审核风险检查。

用户反馈生成 skill:

- 用户输入"以后帮我重点看前三分钟钩子"。
- 系统生成 skill draft。
- 用户确认保存。
- 下一轮报告出现该 skill 的分析区块。

### 7.4 Demo 证据

评估方能看到:

- skill 列表。
- 保存一个新 skill。
- 应用 skill 后报告新增或重排对应分析。

### 7.5 取舍

不做模型训练,不做跨用户共享技能市场。先做当前项目级 skill,保证可解释和可演示。

## 8. 加分项 6:真实场景前端展示

### 8.1 目标

前端本身提升理解效率,不是普通聊天壳。

### 8.2 最小可交付

页面:

- 上传页。
- 报告页。

报告页组件:

- 原文阅读器。
- 决策卡片。
- 评分卡。
- 剧情时间线。
- 人物关系。
- 视角切换。
- 证据高亮。
- 追问聊天。
- 改写面板。
- feedback/skill 面板。

### 8.3 设计原则

- 左原文,右分析。
- 结论必须可点证据。
- 30 秒层、3 分钟层、10 分钟层分清。
- 不用复杂视觉牺牲信息密度。

### 8.4 Demo 证据

评估方能明显感受到:

- 比纯文本报告更快。
- 比聊天框更可定位。
- 比摘要更能决策。
- 每个结论都能查原文。

## 9. 加分项之间的依赖

前端展示依赖:

- 报告 schema。
- evidence refs。
- scorecard。

数据分析依赖:

- segment extraction。
- aggregation。
- evidence refs。

改写依赖:

- scorecard。
- low-score detection。
- selected segment。

skill 机制依赖:

- feedback。
- prompt/template registry。
- report generation。

评估依赖:

- stable schema。
- fixtures。
- golden labels。

部署依赖:

- API 可运行。
- Web 可构建。
- env 配置清晰。

## 10. 最终展示顺序

最终面试展示建议顺序:

1. 打开线上 demo,证明可部署。
2. 加载示例剧本,证明可输入。
3. 展示决策卡和 coverage,证明不是摘要。
4. 点击证据,证明可验证。
5. 切换视角,证明服务不同岗位。
6. 展示 scorecard,证明数据分析。
7. 追问一个问题,证明 Agent 交互。
8. 改写低分片段,证明改写能力。
9. 保存一个 skill,证明可进化。
10. 展示 eval report,证明有评估方法。

这条顺序能把所有加分项自然串起来。
