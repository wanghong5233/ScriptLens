剧级标签来源在业界并存两条路径：剧本文本提取与榜单/曝光后验聚合。最小标签单元粒度从 shot、clip、scene 到 event 均有实践。

## 2. 剧本结构实证

样本：100 集 210 场，自动统计如下。

| 指标 | 数值 |
| --- | --- |
| 总集数 | 100 |
| 总场数 | 210 |
| 每集场数 min / median / max | 0 / 2 / 5 |
| 每场行数 min / median / max | 1 / 15 / 75 |
| △ 动作描述总数 | 1316 |
| OS / VO 内心独白总数 | 226 |
| 对白行数 | 1981 |

剧本格式：每场以 `\d+-\d+ <地点> <日/夜> <内/外>` 开头，后跟 `人物：...`，再交替 `△ 动作描述` / `角色：台词` / `角色OS：` / `角色vo：`。闪回包在 `【闪回开始】` / `【闪回结束】` 之间（实例：81-2）。这些结构信号供 LLM 上下文用，**不作为业务对象建模**。

「场」与「情节」多对多：

- 一场 1~7 个情节单元。短过渡场只有 1 个（实例 40-2，6 行 = 1 个情节）；长高潮场达 5~7 个（实例 1-1，38 行 = 4 个情节）。
- 一条情节弧可跨多场。实例「工地死人案」= 78-x → 79-x → 80-1 → 81-1 → 81-2 闪回 → 82-1，共 6 场。

本文的 `plot_unit` 对应剧作语境里的 **story beat / plot event**：发生了可感知变化的最小叙事动作。变化可以是目标变化、信息揭示、冲突推进、权力关系变化、情绪转折、爽点兑现、悬念设置或风险升高。

边界规则：

- `plot_unit` 不是 episode。一集是播出/切分容器，通常包含多个 plot_unit。
- `plot_unit` 不是 scene。一场由时间地点连续性定义，场内可包含多个 story beat；同一情节弧也可跨多场连续推进。
- `plot_unit` 不是 reward event。reward event 只覆盖打脸、反转、复仇、身份揭露等高价值节点；plot_unit 覆盖全部有效叙事动作。
- `plot_unit` 不是全剧 beat sheet。beat sheet 是开局、催化、中点、高潮、收束等宏观结构节点；plot_unit 是给情节标签和视频 segment 对齐的细粒度载体。
- 没有叙事变化的文本段不生成 plot_unit。正常有对白/动作推进的一集至少有 1 个 plot_unit；无聊或水的剧集通常是低显著性 plot_unit，而不是没有 plot_unit。只有纯标题、重复铺陈、气氛描写、无目标变化的过场，才允许 0 个有效 plot_unit。

业务对象层级：

```text
script（剧）
├── drama_tags  剧级题材，开放多选（来源：llm / human_correction / external_import）
├── character_graph（人物关系图，来源：规则抽取 + LLM 关系判定 + 人工修正）
│   ├── characters            canonical character nodes
│   └── relationships         pairwise / dynamic relationship edges
└── episode（集，仅作为切分容器，不挂业务标签）
    └── plot_unit（情节单元，业务对象，标签载体）
        ├── summary           一句话描述
        ├── line_range        [line_start, line_end]
        ├── hints             location / time_of_day / in_out / characters（场结构信号，仅供描述）
        ├── participants      本情节参与人物及其作用（actor / target / helper / observer）
        └── tags 16 维 enum（每个 plot_unit 同时拥有 16 个标签字段）
            ├── asr 6 维      dialogue_density / speech_style / cta_type / voiceover_type
            │                 emotional_keywords / keyword_theme
            ├── plot 原始 6 维 plot_hook / conflict_type / story_stage / relationship_arc
            │                  payoff_type / emotional_driver
            └── plot 派生 4 维 business_content_archetype / business_conflict_bucket
                              business_payoff_bucket / business_emotion_bucket
```

抽取方向：**先抽 plot_unit，再给 plot_unit 打标签**。plot_unit 是故事里的自然叙事单元，标签是它的属性；不按标签集合反向扫描剧本。原因：

- 同一个 plot_unit 可同时具备冲突、爽点、情绪、台词等多维属性；
- 先按标签扫描会导致同一段文本被不同标签重复切片，边界不稳定；
- 视频侧 storyboard cut / highlight clip 也是先形成片段，再在片段上附加 visual/asr/plot 标签。

业界做法是对同一片段挂多组结构化属性，而不是只贴一个标签。MovieGraphs 的单个 clip 同时包含 situation label、scene label、人物、属性、关系、互动、原因、时间戳；FilmGraph 的单个 shot/scene 同时包含 cinematography、visual、audio、editorial、event；Eluvio Tagger 也按 frame/segment/shot 聚合多类视觉、OCR、语音标签。

因此一个 plot_unit 拥有 **16 个候选标签维度**：6 个 asr + 6 个 plot 原始 + 4 个 plot 派生。它们是结构化特征字段，不等于前端要展示 16 个有效标签 chip。字段默认单选 top-1，可取 `none` / `unclear` 这类空值；前端默认展示 4 个 business 维度，asr 与原始 plot 维度进入详情/审计视图。剧级 drama_tags 另挂在 script 上，多选。

人物关系图是独立产物，不属于 `素材标签体系.md` 的 plot 标签；但它为 plot_unit 抽取提供上下文，plot_unit 也为人物关系变化提供证据。

## 3. ScriptLens 产出的标签矩阵

剧本是纯文本。`素材标签体系.md` 共 5 大类标签，按 ScriptLens 是否能从剧本文本稳定产出来划分如下。

| 类别 | 载体 | ScriptLens 产出 | 理由 |
| --- | --- | --- | --- |
| 剧级 `drama_tags` | script | **是**（多选） | 剧本是上游事实源；业界普遍用 NLP 从剧本文本抽剧级题材；榜单数据是后验聚合，不应作为唯一来源。 |
| 画面 `visual_tags`（19 维） | 视频片段 | **否** | 色温、光线、镜头、调色、亲密度、出镜人数等需视频帧。 |
| ASR 台词 `asr_tags`（6 维） | plot_unit | **是** | 剧本本就携带台词文本与 OS/VO；6 维（密度、风格、CTA 钩子、旁白类型、情绪词强度、主题）都能从台词层判断。注意载体是 plot_unit，**与素材侧的 asr_tags（30-60s 片段级）共享 enum，不共享对象**。 |
| 情节原始 `plot_*`（6 维） | plot_unit | **是** | 6 维（plot_hook / conflict_type / story_stage / relationship_arc / payoff_type / emotional_driver）字面就是叙事文本维度。 |
| 情节派生 `business_*`（4 维） | plot_unit | **是** | 文档明确「业务粗粒度 plot 标签由原始细粒度 plot 标签派生」。默认进入价值模板榜。 |
| 剪辑 `cut_*`（3 维） | 视频片段 | **否** | 时长、分辨率、剪辑节奏，视频专属。 |

ScriptLens 标签产出汇总：1 个剧级开放多选 + 16 个情节单元候选维度（6 asr + 6 plot 原始 + 4 plot 派生）。人物关系图是独立产物，不计入 16 维标签。

## 4. 多标签规则

| 问题 | 决策 | 依据 |
| --- | --- | --- |
| 剧级 drama_tags 是否多选 | 是，多选 | 文档 §1 的剧级集合就是一长串候选（重生 + 总裁 + 现代言情 + 大女主 + 都市 + 复仇 ...），一部剧本就携带多个题材属性。 |
| 16 个 plot_unit 维度每维是否多选 | 默认单选 top-1，可取 none / unclear | LLM 稳定性优先；schema 用 list[Literal] 兼容未来开多选。 |
| 一集是否可有多组 plot_unit 维度 | 是。一集含 N 个 plot_unit，就有 N 组 16 维特征。 | 标签载体在 plot_unit。 |
| 6 原始与 4 派生展示是否嵌套 | 否，并列展示。business_* 默认显示，原始 6 维放在"详情/审计"折叠区。 | 派生关系 ≠ 父子结构；价值模板榜口径平铺。 |

## 5. 人工标注

人工标注与模型输出共用 §10 的 `plot_unit_tags` / `script_tags` 表，复用同一套 enum，通过 `source` 字段区分（`llm` / `human_correction` / `external_import`）。`rule_derived` 仅用于离线对照评测，不作为主链路读取来源。同一 `(plot_unit_id, dim)` 允许多行并存。

读取优先级 `human_correction > llm`；存在 `human_correction` 时 `llm` 行保留用于 diff 与评测。评测以 `human_correction` 作为金标准计算每维 Kappa。

## 6. 情节与视频粒度

### 6.1 视频侧对象层级

| 层 | 典型时长 | 说明 | 标签特征 |
| --- | --- | --- | --- |
| 原片 episode video | 1-5 min | 单集正片 | 不直接作为情节反查对象 |
| 镜头 shot | 1-10 s | 摄影/剪辑上的连续画面 | 适合 `shot_type`、`color_temperature`、`lighting_style` 等纯视觉标签 |
| 叙事片段 segment / storyboard cut / highlight clip | 5-30 s | 有起止时间、OCR/ASR、剧情描述、高光分；火山引擎 `Storyboard` / `HighlightCuts.Cuts` 属于这一层 | 最接近剧本 `plot_unit` |
| 投流素材 material / edit | 15 s-7 min | 多个叙事片段混剪后的广告素材或宣传片，可直接投放 | 适合 `duration_bin`、`cut_pace`、`opening_type`、聚合后的 visual/asr/plot 标签 |

`素材标签体系.md` 的 visual 标签覆盖了 shot 与 material 两种口径：`color_temperature`、`lighting_style`、`shot_type` 更贴近镜头/片段；`opening_type`、`duration_bin`、`cut_pace` 更贴近投流素材整体。字段里出现 `mixed`，说明一个被打标对象可以包含多个镜头、多个场景或多段内容。

### 6.2 plot_unit 的视频对应层

剧本 `plot_unit` 对应视频侧的**叙事片段 segment / storyboard cut / highlight clip**，不是整条投流素材。依据：

- `plot_unit` 是一次戏剧动作、一次信息揭示、一次冲突推进或一次情绪转折；
- 火山引擎 `Storyboard` 片段包含起止时间、OCR 字幕、剧情描述、高光分，与 `plot_unit.summary + line_range + tags` 最接近；
- 投流素材通常由多个叙事片段混剪而成，一条素材可包含多个 plot_unit，一个 plot_unit 也可被复用进多条素材。

对象关系：

```text
script.plot_unit
  └── semantic match
      └── video.segment / storyboard_cut / highlight_clip
            └── used_by
                └── video.material / edit（投流素材）
```

### 6.3 本期对接方式

本期没有视频时间码和 storyboard 明细表时，先做**标签语义反查**：

1. 输入：plot_unit 的 16 维标签 + 剧级 drama_tags
2. 匹配：同 drama_id 下，命中相同 drama / asr / plot 标签的视频片段或素材模板
3. 返回：命中的视频片段/素材、模板效果分、曝光、互动率、置信度

存在 storyboard/cut 明细数据时，优先返回 segment 级结果；只有 material/template 聚合数据时，返回 material 级结果并标记为 `aggregate_match`。

## 7. 人物与人物关系

人物关系是 ScriptLens 的独立分析产物，不进入 `plot_unit_tags` 的 16 维标签表。它与情节抽取共享 `script_ir`，并通过 `plot_unit_participants` 与 plot_unit 发生关联。

业界成熟做法通常采用分阶段流水线：

```text
结构 IR
  ├── 人物实体识别 / 别名归一 / 共现网络
  ├── plot_unit / event 抽取
  ├── event participation（谁参与了这个情节，以什么角色参与）
  └── relationship graph（关系类型、极性、强度、随剧情变化）
```

### 7.1 与情节标签的关系

| 对象 | 是否属于标签 | 与 plot_unit 的关系 |
| --- | --- | --- |
| character | 否 | plot_unit 的参与者 |
| relationship | 否 | plot_unit 的上下文和可能被改变的状态 |
| plot_unit tag | 是 | 描述本情节的冲突、爽点、情绪、台词属性 |
| event participation | 否 | 连接 character 与 plot_unit，记录 actor / target / helper / observer 等作用 |

两条链路相互依赖但不合并：

- 人物关系图帮助判断 `relationship_arc`、`conflict_type`、`emotional_driver`。
- plot_unit 的 action/dialogue/evidence_lines 是关系变化的证据。
- 人物关系不是筛选 plot_unit 的标签条件，而是图谱对象和解释上下文。

### 7.2 当前实现评估

现有 `character_graph_chain.py` 的方法是「共现矩阵 + LLM 关系分类」：

- 共现统计决定主要人物和候选边；
- LLM 补充 `role / motivation / goal / obstacle / relationship type / polarity`；
- LLM 失败时降级返回纯共现图。

这个实现适合作为 MVP，但需要升级：

| 问题 | 影响 | 优化方向 |
| --- | --- | --- |
| 只基于 scene 共现 | 同场不代表有关系；跨场强关系可能被低估 | 引入 dialogue 对话对象、action 中的施事/受事、plot_unit participation |
| 静态关系图 | 无法表示先敌后友、误会解除、背叛等关系变化 | 增加 relationship_snapshots / dynamic edge |
| 缺少别名归一 | `云先生 / 云逸楚 / 云总` 可能分裂成多个节点 | 增加 alias 表和 canonical character id |
| 缺少证据行 | UI 和评测无法解释关系判定 | 每个节点/边保留 evidence_lines / plot_unit_ids |
| 关系类型偏粗 | 难表达短剧常见的利用、复仇、养亲、上下级、婚约 | 扩展关系 type，保留 polarity 与 strength |
| 与 plot_unit 脱节 | 人物图无法支持情节级检索和视频匹配 | 增加 plot_unit_participants |

### 7.3 抽取策略

人物关系链路按四步执行：

1. **候选人物抽取**：从 `人物：` 行、对白 speaker、OS/VO speaker、action 中高频人名抽候选。
2. **别名归一**：规则合并称谓（先生/总/爸/妈/堂姐等）+ LLM 判定低置信别名。
3. **plot_unit participation**：对每个 plot_unit 判断参与人物及作用：`actor / target / helper / observer / mentioned`。
4. **关系图聚合**：从 participation、对话方向、action 施受关系、冲突/保护/欺骗证据聚合 `relationship type / polarity / strength / evidence`。

输出分两类：

- `character_entities`：人物节点，稳定 canonical id。
- `character_relationships`：关系边，可按 episode 或 plot_unit 形成动态快照。

## 8. 抽取流程

成熟剧本解析流水线通常先做结构解析，再做语义抽取：

| 参考 | 可借鉴做法 |
| --- | --- |
| ScreenPy / Fountain parser | 先把剧本转成 scene heading、action、dialogue、parenthetical、transition 等结构化元素 |
| Hierarchical Encoders for Screenplays | 分开编码 action 与 dialogue，再按 scene/script 层级聚合 |
| Fabula / Story2KG | 两遍处理：预处理成标准 JSON，再抽 entity、event、relationship、emotion |
| hierarchical multi-label classification | 长文档标签先候选召回/分块聚合，再做 LLM rerank / select |

因此抽取流程拆成两条共享 IR 的链路：**结构 IR → 人物关系图**，以及 **结构 IR → plot_unit → plot_unit 标签 → 剧级标签**。两条链路通过 `plot_unit_participants` 相互连接。

### 8.1 结构 IR（确定性）

输入：docx/pdf/txt 解析后的段落列表。

输出：

```text
script_ir
├── episodes[]
│   ├── episode_no
│   ├── line_range
│   └── blocks[]
│       ├── scene_heading   # 1-1 仙境会所包厢 夜 内
│       ├── character_list  # 人物：慕梦汐、云逸楚
│       ├── action          # △ 动作描述
│       ├── dialogue        # 角色：台词
│       ├── voiceover       # 角色vo：
│       ├── inner_voice     # 角色OS：
│       └── flashback_mark  # 【闪回开始/结束】
```

规则：

- `第N集` 切 episode。
- `\d+-\d+ <地点> <日/夜> <内/外>` 解析为 scene hint。
- `人物：` 解析为 characters hint。
- `△` 行归为 action。
- `角色：` 归为 dialogue；`角色OS：` 归为 inner_voice；`角色vo：` 归为 voiceover。

此层不调用 LLM，结果用于后续所有抽取、缓存和审计。

### 8.2 plot_unit 切分（LLM + 结构约束）

输入：单集 `script_ir.episodes[i]` + 前 3-5 集 plot_unit summary。

任务：把一集内的 blocks 切成有叙事意义的 plot_unit。切分标准：

- 一次明确目标变化、信息揭示、冲突推进、权力关系变化、情绪转折、爽点兑现或悬念设置；
- plot_unit 可跨 scene hint，但必须落在同一 episode 内；
- 每个 plot_unit 输出 `line_range`，不得重叠，不得越界。
- 无叙事变化的段落归入相邻 plot_unit 的上下文，不单独成单元；整集只有标题/空白/重复气氛描写时，可返回空列表并记录 `no_effective_plot_unit`。

输出字段：

- `summary`
- `line_range`
- `location_hint / time_of_day_hint / in_out_hint / characters_hint`
- `evidence_lines`

### 8.3 plot_unit 标签抽取（三路）

同一个 plot_unit 的 16 维标签分三路抽取，避免把所有维度混成一次大分类。

#### 8.3.1 ASR 台词标签（6 维）

输入：plot_unit 内的 dialogue / voiceover / inner_voice 文本。

| 维度 | 方法 | 依据 |
| --- | --- | --- |
| dialogue_density | 规则计算 + 统一结构化落库 | 台词字数 / plot_unit 总字数，分 dense / moderate / sparse / none |
| voiceover_type | 规则计算 + 统一结构化落库 | voiceover / inner_voice 是否存在及占比，分 character / narrator / mixed / none |
| emotional_keywords | 词典 + LLM 校验 | 情绪词密度先规则计数，边界样本交给 LLM |
| speech_style | LLM 单维分类 | emotional / dramatic / narrative / comedic / none |
| cta_type | LLM 单维分类 | curiosity / urgency / subscribe / none |
| keyword_theme | LLM 单维分类 | romance / power / family / comedy / none |

输出统一写入 `plot_unit_tags(source='llm')`。规则统计值仅作为抽取过程中的确定性计算步骤，不单独写入 `rule_derived` 行。

#### 8.3.2 plot 标签（10 维，单次 LLM 输出）

输入：plot_unit 的 action + dialogue + summary + 前后相邻 plot_unit summary。

LLM 一次输出 10 个维度：

- `plot_hook`
- `conflict_type`
- `story_stage`
- `relationship_arc`
- `payoff_type`
- `emotional_driver`
- `business_content_archetype`
- `business_conflict_bucket`
- `business_payoff_bucket`
- `business_emotion_bucket`

每个维度必须同时输出 `value`、`confidence`、`evidence_lines`。`story_stage` 依赖 episode 内位置与前后 plot_unit，不能只看当前片段。

主链路写库：上述 10 维统一写入 `plot_unit_tags(source='llm')`。

#### 8.3.3 business 4 维对照基线（离线评测）

输入：6 个 plot 原始标签 + plot_unit summary。

主链路 + 对照基线并行：

| 路径 | 方法 | 用途 |
| --- | --- | --- |
| 主链路 LLM | 使用 §8.3.2 单次 LLM 输出中的 4 个 `business_*` 结果 | 正式写库结果，纳入稳定性门槛 |
| 规则基线 | ScriptLens 内置确定性映射函数（由 `plot_hook/conflict_type/payoff_type/emotional_driver` 映射到 `business_*`） | 仅用于离线 PAR / Kappa 对照，不作为线上读取来源 |

默认线上读取 `llm` 行；规则基线只进入实验报告附录。

输出 JSON（每个 plot_unit 一项）：

### 8.4 剧级 drama_tags（聚合分类）

剧级标签不直接把整本剧本塞给 LLM 分类，而是先汇总结构化证据：

输入：

- 全部 plot_unit summary
- 主要人物关系图（从 characters_hint 与互动频次生成）
- plot 原始/业务标签的计数分布
- 高置信 plot_unit 样例（每类 business_* top evidence）
- `素材标签体系.md` §1 剧级候选标签集合

流程：

1. 候选召回：规则召回 + embedding 相似度召回 + LLM 候选召回，合并 top-K。
2. LLM rerank：逐个候选判断是否成立，输出 `value/confidence/evidence_unit_ids`。
3. 后处理：同义标签去重，保留高置信多选结果。

输出：`script_tags(dim='drama_tags', value, source, confidence, evidence_unit_ids)`。

### 8.5 稳定性堆栈

OpenAI / Azure OpenAI 文档均说明 hosted LLM 即使在 `temperature=0`、固定 `seed` 下也只能做到近似稳定；structured output 只能保证 JSON/schema 合法，不能保证多次运行选择同一个 enum。稳定性需要由输入确定性、schema 约束、重复采样投票和版本化缓存共同保障。

| 层 | 措施 | 作用 |
| --- | --- | --- |
| 1 IR | 所有 LLM 输入都来自确定性的 `script_ir`，不直接读原始 docx | 消除解析漂移 |
| 2 prompt | enum 定义、判定规则、正反例随 prompt 全量传入，记录 `prompt_ver` | 降低语义漂移 |
| 3 schema | `response_format: json_schema`，enum 字段用 `Literal[...]` | 保证 JSON 结构合法 |
| 4 guided decoding | 自部署时使用 vLLM `guided_json` + outlines/xgrammar | 保证 enum 不越界 |
| 5 self-consistency | N=5，plot/asr 每维独立 majority vote，平票按低置信处理 | 量化稳定性 |
| 6 cache | key = `hash(input_ir) + prompt_ver + tag_set_ver` | 复现与成本控制 |

异常处理：JSON 解析失败重试 1 次；enum 越界改写为该维默认值并记录告警；`line_range` 重叠或越界时整集重试。

## 9. 评测口径

评测脚本：`ScriptLens/backend/eval/plot_tag_eval.py`。

成熟评估口径分四层：**人工标注可靠性 → 切分质量 → 标签准确性 → 复现/一致性**。

执行分阶段：

| 阶段 | 阻断门槛 | 是否依赖人工金标 |
| --- | --- | --- |
| Batch 1（先跑通） | 复现稳定性（§9.4）+ 切分自一致性（§9.2 Batch 1） | 否 |
| Batch 2+（校准上线） | §9.2 + §9.3 + §9.4 全量门槛 | 是 |

### 9.1 金标集

| 数据集 | 构造方式 | 用途 |
| --- | --- | --- |
| gold_dev | 20 集，双人独立标注 + 仲裁 | prompt / 规则迭代 |
| gold_test | 30-50 集，冻结不参与调参 | 上线验收 |
| consistency_set | 50-100 组相似情节，每组 3-5 个 plot_unit | 相似情节标签一致性 |
| regression_set | 历史失败样本 + 边界样本 | prompt / 模型升级回归 |

人工标注先评估 IAA（inter-annotator agreement）：

- plot_unit 切分：WindowDiff / Pk + boundary F1。
- 单选 enum：Cohen's Kappa；3 人以上或缺失标注用 Krippendorff's Alpha。
- drama_tags 多选：Jaccard、micro/macro F1；多标签 Kappa 只作参考。

IAA 未达标的维度先补标注规范，不进入模型验收。

### 9.2 plot_unit 切分质量

| 指标 | 计算 | 说明 |
| --- | --- | --- |
| boundary F1 | 预测边界与人工边界匹配，允许 ±1 block 容差 | 衡量切分点是否准确 |
| WindowDiff / Pk | 文本分割通用指标，window size = 人工平均 plot_unit 长度 / 2 | 惩罚漏切、误切、近邻错切 |
| span IoU | 预测 plot_unit 与人工 plot_unit 做最大匹配后算 line_range IoU | 衡量片段覆盖程度 |
| count MAE | 每集预测 plot_unit 数 vs 人工 plot_unit 数 | 防止系统性过切/少切 |

阶段门槛：

- Batch 1（无金标）：5 seed pair-wise boundary F1 ≥ 0.70（自一致性门槛）。
- Batch 2+（有金标）：boundary F1 ≥ 0.75、WindowDiff ≤ 0.25、count MAE ≤ 1.0 / episode。

### 9.3 标签准确性

先用 span IoU ≥ 0.5 将预测 plot_unit 匹配到人工 plot_unit，再评估标签。

| 标签层 | 指标 | 说明 |
| --- | --- | --- |
| drama_tags | Jaccard、micro/macro F1、top-K recall | 多选剧级标签 |
| asr 6 维 | accuracy、macro F1、Cohen's Kappa | 规则维度和 LLM 维度分开报 |
| plot 原始 6 维 | accuracy、macro F1、Cohen's Kappa | 每维单独报，不只报平均值 |
| business 4 维 | accuracy、macro F1、Cohen's Kappa | 榜单口径核心指标 |
| evidence_lines | evidence 命中 gold span 比例 | 防止标签对但证据错 |

阶段门槛：

- Batch 1：本节指标记录但不作为阻断门槛（无人工金标阶段）。
- Batch 2+：business 4 维平均 Kappa ≥ 0.6、单维 Kappa ≥ 0.5；plot 原始 6 维平均 Kappa ≥ 0.5；asr 6 维平均 Kappa ≥ 0.5；drama_tags Jaccard ≥ 0.6。

### 9.4 复现稳定性

同一 `script_ir + prompt_ver + tag_set_ver + model` 重复运行 N=5。

| 指标 | 计算 | 说明 |
| --- | --- | --- |
| TARa@5 | parsed JSON 后 5 次输出完全一致的样本比例 | 避免 raw string 差异干扰 |
| Fleiss' Kappa@5 | 将 5 次运行视为 5 个标注员，每维计算 Kappa | 衡量重复运行一致性 |
| vote entropy | 每维 5 次投票分布熵 | 找不稳定维度 |
| majority margin | 第一名票数 - 第二名票数 | 低 margin 样本进入人工复核 |
| max-min diff | 同一评测集 5 次 accuracy 最大最小差 | 防止只汇报一次幸运结果 |

Batch 1 的阻断门槛以本节为准：

- business 4 维 TARa@5 ≥ 0.85
- business 4 维 Fleiss' Kappa@5 ≥ 0.75
- max-min diff ≤ 0.03

### 9.5 相似情节一致性

`consistency_set` 用人工或 embedding 预聚类，再人工确认每组确实是同类情节。每组内期望标签一致的维度：

- `plot_hook`
- `conflict_type`
- `payoff_type`
- `emotional_driver`
- 4 个 `business_*`

上下文敏感维度单独评估：`story_stage`、`relationship_arc`、ASR 6 维。相似情节在不同集数位置可能处于不同 `story_stage`，不能强制完全一致。

| 指标 | 计算 | 说明 |
| --- | --- | --- |
| cluster purity | 每组内多数标签占比 | 衡量同类情节是否稳定给同类标签 |
| pairwise consistency | 同组内两两标签相同的比例 | 对组大小不敏感 |
| label entropy | 同组内标签分布熵 | 发现易混维度 |
| contradiction rate | 同组内出现互斥标签的比例 | 例如同一类打脸情节一部分标 `face_slapping`，一部分标 `romantic_payoff` |

上线门槛：

- business 4 维 cluster purity ≥ 0.85
- plot 原始稳定维度 cluster purity ≥ 0.75
- contradiction rate ≤ 0.1

### 9.6 回归报告

每次变更 `prompt_ver`、`tag_set_ver`、模型或派生规则时输出报告：

```text
eval_report
├── gold_dev_metrics
├── gold_test_metrics
├── stability_metrics
├── consistency_metrics
├── per_dimension_confusion_matrix
├── low_confidence_cases
├── changed_predictions_vs_previous_version
└── blocker_regressions
```

阻断条件：

- gold_test 任一核心指标低于上线门槛
- business 4 维任一维度较上一版本 Kappa 下降 > 0.05
- consistency_set contradiction rate 上升 > 0.05
- JSON/schema 失败率 > 1%

## 10. 数据库 schema

外部 schema 交叉验证：

## 11. 与现有 highlights 实现的处置

ScriptLens 当前 highlights 是 demo，与本设计不对齐：

- 字段集不是 `素材标签体系.md` 的 enum；
- 粒度是「场或场片段」而非情节单元；
- `pacing_curve.event_count` 是 `reward_events + hook 词 + twist 类型` 的按集聚合指标，只能反映节奏高低，不能作为 plot_unit 数量或情节标签载体；
- `beat_sheet` 是全剧三幕宏观骨架，只有 5-9 个关键节点，不能替代细粒度 plot_unit；
- 没有版本号、缓存、稳定性约束；
- 不分 source。

处置：highlights 不再迭代，旧表数据只读，新链路完全独立。前端在过渡期可同时展示「情节标签」与「旧版看点」两个 section，3 周后移除旧版。

### 12.1 曲线展示

当前节奏曲线有保留价值，但不能改名为「情节曲线」。它回答的是「哪几集更密、更燃、更有高光」，不回答「情节单元如何切分、每个情节是什么标签」。

成熟产品常见三类曲线：

- **节奏 / 强度曲线**：按 scene、episode 或时间片聚合 tension / pacing / high-score，用于发现平淡段、峰值过早、高潮不足。Quanten Arc、Scriptsee、StoryGraph Lab 都采用类似 scene-by-scene intensity / pacing time-series。
- **情绪曲线**：按时间展示 joy / fear / anger / sadness / tension 等强度，用于判断类型片情绪是否匹配。DraftZero、Scriptsee、影视剪辑类工具常用 emotion arc。
- **高光曲线 / 高光分**：视频侧按 storyboard / clip 输出 score、起止时间、字幕和剧情描述。火山引擎短剧高光智剪、腾讯云精彩集锦、百度智能集锦公开能力都属于这一类。

ScriptLens 前端采用两层展示：

1. **节奏曲线**保留在概览/故事页。当前数据源 `pacing_curve.event_count = hooks + twists + reward_events`，准确名称是「高光密度曲线」或「事件密度曲线」；如果 UI 继续叫「节奏曲线」，必须在 tooltip 说明它是节奏的代理指标，不是完整 pacing 评分。
2. **情节序列**新增在情节标签页，以列表/时间轴展示 plot_unit，不用单独命名为曲线。每个点是一个 plot_unit，展示 summary、业务标签、证据行和视频反查入口。

当前实现评估：

| 项 | 当前实现 | 专业性判断 |
| --- | --- | --- |
| x 轴 | episode | 适合短剧 100 集全局扫描；不适合定位场内/片段级节奏 |
| y 轴 | `hooks + twists + reward_events` | 可解释、稳定，但只代表高光/反转密度，不等于完整 pacing |
| spike 阈值 | `>= max * 0.7` | 易读，但受异常峰值影响；后续应改为 z-score / percentile |
| sentiment | 正负词典粗算 | 可做辅助 tooltip，不宜称为情绪曲线 |
| 缺失信号 | scene length、dialogue/action density、plot_unit density、tension rise/fall、downtime | 这些是成熟 pacing 分析常用信号 |

专业定义下的 pacing 是「故事展开速度与张弛节奏」，不是单纯事件数。成熟剧本分析通常看：

- 单位篇幅内有效 story beat / plot event 的密度；
- scene 长度与长短场分布；
- dialogue/action 密度；
- 冲突、风险、信息揭示、反转、爽点的出现位置；
- rising action / falling action 的张弛结构；
- 高强度节点之间的 downtime 是否过长或过短。

因此本期保留当前曲线作为高光密度视图；实现 `plot_unit` 后升级为 pacing v2：

```text
pacing_intensity =
  w1 * plot_unit_density
+ w2 * hook_or_reversal_score
+ w3 * conflict_or_stakes_score
+ w4 * payoff_or_emotion_score
+ w5 * dialogue_action_density
- w6 * downtime_penalty
```

v2 曲线同时输出分项：`plot_unit_count / highlight_count / conflict_score / payoff_score / dialogue_density / downtime_flag`。前端默认展示总强度，tooltip 展示分项，避免把黑盒分数伪装成客观事实。

后续如需要「情节曲线」，应定义为从 plot_unit 派生的第二层可视化，而不是把现有节奏曲线改名：

- x 轴：plot_unit 顺序或 episode；
- y 轴：narrative_intensity，可由 `plot_hook / conflict_type / payoff_type / emotional_driver` 加权得到；
- 标注：business_* 标签、人物关系变化、视频 segment 匹配结果；
- 用途：观察全剧情节推进是否存在长时间低强度、高潮过密、反转堆叠或情绪断层。
